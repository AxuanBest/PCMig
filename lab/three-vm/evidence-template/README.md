# evidence-template\ —— 证据采集格式

> 目的：让每次实验产出的证据**可复验、可追溯、可对照**，避免「同一个 Bug 几十张近似图、却回答不了当时为什么这么改」。

## 一、一个证据包的最小构成

```
<批次名>-<日期>/
├── README.md            本批次的「问题 → 结论 → 证据」摘要
├── manifest.txt         逐文件 SHA256 + 采集时间 + 采集脚本
├── 命令与参数.txt        实际执行的命令行、脚本全文、环境变量
├── 结果/
│   ├── 复现证据/         故障类：连续 3 次
│   └── 修复证据/         故障类：修复后回归 3 次（**必须与复现证据方法不同**）
├── 数值与日志/           job-state.json 快照、诊断日志、Loss Ledger、Flight Recorder 导出
└── 截图/                **每个 Bug 最终只留 1~5 张**（修复前 / 修复后 / 关键对照）
```

## 二、命名与纪律

1. **截图必须带 SELFCHECK**（脚本自校验：窗口标题、元素可达性、时间戳一致）。
2. **屏幕像素归因必须使用同一次运行的 UIA 原点**；跨运行的坐标拼接一律作废。
3. **ROI 锚点只认 `aid=TotalImmersiveProgress`**。
4. 一个 Bug 的证据图**上限 1~5 张**；同一问题连续几十张近似帧、临时放大、鼠标移动重复、自动视觉脚本批量 frame、ROI crop、pixel diff、临时 probe 图**一律不入包**（采集时可直接丢弃，也可放 `_work\` 由批次结束后清除）。
5. **复现证据与修复证据必须两类独立**（不同方法、不同路径、最好不同日期）。
6. 故障类必须**连续复现 3 次 + 修复后回归 3 次**，且正常路径不退化。
7. 数值类证据优先于图像证据：`completedBytes` / `percent` / `bytesPerSecond` / `lastUpdateUtc` / 熔断命中计数必须落**原始文本**（`job-*.jsonl`），不要只截图。
8. 装饰层（Band / 粒子 / Ripple / Halo）**永不许**作为进度真值的判定依据。
9. 视觉终验**永远是人工**；脚本结论只能写「过程证据 / 自动化判定」，不得写「视觉验收通过」。

## 三、批次 README 模板

```markdown
# <批次名>（YYYY-MM-DD）

## 问题
<一句话现象 + 触发条件 + 首次观测时间>

## 根因
<机制级描述：哪个函数、哪一行、为什么> 
<若结论被推翻过，写明旧结论与推翻理由>

## 修复
<commit / 文件 / 关键 diff>

## 证据
- 复现：<命令 + 3 次结果 + 原始数值>
- 修复后：<命令 + 3 次结果 + 原始数值>
- 对照图：<1~5 张，说明每张在证明什么>

## 未做 / 未测（如实）
<例如：回冲路径未触发（HIT-RETRACT=0）；未做真实物理机复验；未做人工视觉终验>

## 回退
<备份路径 / git revert / 恢复步骤>
```

## 四、存放位置

| 类型 | 位置 |
|---|---|
| 正式证据（canonical） | `<实验室根>\Evidence\<主题>\` |
| 历史证据批次（仓库内） | `PCMig\archive\evidence\<批次>\` |
| Bug 根因与修复资料 | `PCMig\archive\bug-evidence\<topic>\` |
| 复验包 | `<工作区根>\archive\review-packages\<topic>\` |
