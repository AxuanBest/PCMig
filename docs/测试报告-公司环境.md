## 测试中发现并已修复的问题
1. **【严重】空计划假成功**：选定路径全部不存在时显示"✔ 迁移完成 0B"。

## 补测：v0.2.10 报错可诊断性（2026-09-15 上午，公司域环境实战复现）

背景：用户迁移 26/27 对象时，失败对象在报错框里只显示"**复制失败**"四个字，无法判断是哪个文件、什么原因。

### 根因
1. `ErrorTranslator.ShortReason` 解析不出错误码时固定返回"复制失败"；GUI 实时报错行传入的是**裸错误码**（如 `"32"`），也走不到码表。
2. RobocopyRunner 只保留**最后一行**含"错误"的输出，多文件失败时"哪个文件、什么错误"全部丢失；
   robocopy 收尾的"错误: 超过重试限制。"是汇总提示行，不含错误码 → 直接落进"复制失败"。

### 修复
- 收集**全部**失败行（上限 500 行防爆内存），统计错误码分布 + 抽样例文件，产出：
  `N 个文件复制失败：<主因>（错误码 M）；例如：a、b、c。robocopy 退出码 11（位掩码…）`
- 集中错误码表 `ReasonForCode`（32 占用 / 5 权限 / 67 找不到网络名 / 112 空间不足 …），裸码也走码表。
- 兜底永不返回"复制失败"：解析不出码就原样带出报错原文。
- `pcmig status` 增加"未完成/有错误的对象"清单（对象 + 源路径 + 具体原因 + robocopy 退出码）。
- 恢复时"共享被关闭"的报错改为点名真正连不上的共享（原先报 IPC$ 的 `找不到网络名`，误导排查方向）。

### 验证（两种独立方法）
| 方法 | 做法 | 结果 |
|---|---|---|
| 1 真实日志驱动 | 独立测试程序（ErrorReasonTest）引用 PCMig.Core，喂入**真实失败日志** object-000016.log 的 172 行错误 | 输出 `129 个文件复制失败：文件被占用（…）（错误码 32）；例如：D$\SystemCache\Temp\kmc7832.tmp…`；裸码 `"32"` → `文件被占用（旧电脑上有程序正开着它）`；空/无码入参不再吞成"复制失败" |
| 2 端到端实跑 | CLI `resume` 重跑真实失败对象 → 看任务日志/回执/GUI 报错区 | 回执 `errorDetail` 字段带上完整原因；`pcmig status` 输出：`✘ object-000016 \\192.0.2.23\d\SystemCache / Failed｜66 个文件复制失败：文件被占用 / robocopy 退出码 Bulk=11` |

### 本次未迁移数据的真实性质（结论澄清）
失败对象 SystemCache 本轮 robocopy 汇总：**文件 4368，复制 4，跳过 4342，失败 22**，字节 8.622GB 中跳过 8.382GB，
即**数据已基本全部到位**；失败的是 66 个被旧电脑 Excel/WPS 正在占用的临时文件（`Temp\Diagnostics\EXCEL\*.log`、`INetCache\Content.Word\~WRS*.tmp`）。
关闭旧电脑上的 Excel/WPS（或重启旧电脑）后这些临时文件会自动消失，再点恢复即可 27/27 收尾。
另：\\192.0.2.23\D$ 管理共享在迁移中途被（疑似域策略刷新）关闭，已把任务源改写为同盘的手工共享 \\192.0.2.23\d（27 处路径，原文件留 .bak-dshare 备份）。

## 补测三：v0.2.12 "目标文件夹消失"（2026-09-15 12:30–12:40，本地 UNC 盘根同构复现）

### 现象（用户报告）
迁移完成后，资源管理器里**看不到目标文件夹**，但磁盘空间确实被占用（"数据丢了"的错觉）。

### 根因（已用对照实验锁定）
robocopy 会把**源根目录的目录属性**写到**目标根目录**上，`/DCOPY:T` 拦不住
（真机日志里那行 `错误 67 … 正在复制目标目录属性 <本机临时根>\` 就是它）。
整盘迁移的源根是 **\\主机\D$ 这样的盘根**，而 Windows 盘根天然带 Hidden+System
（本机实测：`C:\ = Hidden,System`、`D:\ = Hidden,System`、`E:\ = Hidden,System,Archive`）。
→ 目标根被标成隐藏 → 资源管理器默认不显示 → 用户"找不到但空间已占"。
**任何整盘迁移都会中招**，已实测踩中 `<本机临时根>`、`<外置测试根>` 两处。

### 对照实验（同构复现，源 = \\localhost\E$\fake-root，其根带 Hidden+System 且有散落文件）
| 条件 | 目标根属性 |
|---|---|
| 对照组：手工 robocopy（未修复逻辑） | `Hidden, System, Directory` ← 故障复现 |
| 只预建目录后 robocopy | `Hidden, System, Directory` ← 预建挡不住 |
| v0.2.12 跑完真实任务 | `Directory` ← 已解除，资源管理器可见 ✔ |

### 修复
`TargetRootGuard.EnsureVisible()` 在三处自动清除目标根的 Hidden/System 并留痕：
传输开始、RootFiles 通道结束后、任务收尾。GUI 新增「 打开目标文件夹」按钮（打开前同样自愈）。
修复日志实测：
```
[WRN] 目标根目录 <外置根>\vis-fix2 原先带 "Hidden, System"（源盘根属性被 robocopy 带过来，
      会导致资源管理器里『看不见但空间已占』），已自动解除隐藏
```

### 验证（交付物本体执行）
- 目标根 `[Directory]`，普通枚举可见 ✔
- L2 校验：`object-000001: 文件 3/3, 字节 234.38 KB/234.38 KB` ✔ 全部通过

## 进度与数据量改进：v0.2.14（2026-09-15 下午）

### 用户反馈（四点）
1. 有失败项时进度条停在 79% 不符合"传输已经结束"的直觉 → 结束后应走满；并要求显示**计划量**与**实际量**；
2. 迁移页「已传/总量」文字显示不全；
3. 底部状态栏百分比与数据量没对齐、颜色不统一，且多出一个百分比；
4. （用户原话末尾为"此外"，待补）

### 改法
- **结束即 100%**：阶段为 Completed / CompletedWithErrors 时进度条直接走满，进度语义 = "这次传输结束了"；
  数据缺不缺由对账行说明，不再卡在 79%。
- **对账行**（迁移页进度条下方）：`计划 41.42 GB · 实际落盘 41.19 GB · 还差 239.27 MB（1 个对象未完成，明细见报错清单）`；
  有缺口时整行变琥珀色，完全一致时绿色。
- **实际落盘的数据口径**（关键）：
  - 已完成对象 = 回执里的目标侧实测字节（TargetBytes）；
  - **失败对象**没有实测值 → 取该对象 robocopy 日志汇总块的「字节」行：**总数 − 失败 = 已落盘**
    （即"已经拷进去、只是没拷完"的部分也算）。这样"还差多少"是真正没落盘的数据，而不是一整个对象的体积
    （实测：SystemCache 对象 8.623 GB 中已落盘 8.39 GB，只有 240 MB 失败）。
  - 汇总块的定位是结构化的：汇总块为"目录/文件/字节"三行、每行恰好 6 个数值，
    取**连续 6 数值行的最长块的第 3 行**。不依赖日志编码（/TEE 重定向为本地代码页、无 BOM），也不依赖中英文界面。
    - 踩坑记录 1：按"含『字节』的最后一行"取 → 取到 `速度: 93,417,362 字节/秒`（3 个数字，实际被跳过）；

### 13.2 关键实验：robocopy 到底能不能覆盖"同大小同时间"的文件

构造 2,000,000 字节文件，目标侧同大小、同时间戳、内容改坏（第 100 字节翻转），逐个开关实测：

| 开关 | 退出码 | 字节行（总数 / 复制 / 跳过…） | 内容是否被源覆盖 |
|------|--------|------------------------------|------------------|
| 默认 | 0 | 1.90 m **0** 1.90 m 0 0 0 | 否 |
| /IS | 0 | 1.90 m **0** 1.90 m 0 0 0 | 否 |
| /IS /IT | 0 | 1.90 m **0** 1.90 m 0 0 0 | 否 |
| /IT | 0 | 1.90 m **0** 1.90 m 0 0 0 | 否 |
| **先删目标侧文件再传（默认开关）** | 1 | 1.90 m **1.90 m** 0 0 0 0 | **是** |

结论（重要）：**/IS、/IT、/IS /IT 在本机 robocopy 版本上对"大小+时间都相同"的文件一律无效**
（字节行"复制=0"，内容没被覆盖）。唯一可靠的做法是**先删掉目标侧那份文件，再让 robocopy 从共享重新拉取**。
v0.2.19 据此实现 PCMig.Core.Transfer.RepairPurge，并已把先前误加的 /IS /IT 开关全部移除（不留无效代码）。

### 13.3 强制覆盖（RepairPurge）的安全边界

只删"本次传输确实会拷贝的文件"，避免删了却没人拷回来：

* 命中排除规则（/XD、/XF，含安全屏蔽名单）的**不删**；
* 云占位符（Skip 策略：Offline / 占位属性）**不删**；
* 重解析点（junction / symlink，robocopy 用 /XJ 不拷）**不删**；
* 大小 ≥ 分流阈值且本次不走 /Z 大文件通道（计划未标记 UseRestartablePass）的**不删**；
* 目标侧本来就不存在的文件无需删（直接新拷）；
* 删除失败（被占用等）不致命：仍由 robocopy 按大小/时间差异决定是否重拷。

日志会记录："强制覆盖: 对象 xxx 已删除目标侧 N 个同名文件（X 字节），将从共享重新拉取"。

## 十四、v0.2.21 ~ v0.2.23 —— 按你的四条实测反馈修正

日期：2026-09-15　交付版本：v0.2.23

### 14.1 反馈一：左栏「报错提示」是"蓝字浅蓝底、对比度低"

根因（v0.2.20 的实现）：报错清单的 ListBoxItem 用的是 WPF 默认模板 —— 悬停/选中态是系统浅蓝高亮，
深色报错文字落在浅蓝底上既糊又低对比；空态"暂无报错"用的是 #94A3B8 灰蓝色。

修正：自定义 ItemContainerStyle（悬停 #FEE2E2、选中 #FECACA，文字颜色不受影响），
行首路径加深为 #7F1D1D + 半粗，原因文字加深为 #92400E，空态改为绿色「✔ 暂无报错」。

实测证据（PrintWindow 让窗口自绘到 DC 后逐像素取色，不是读控件属性）：
面板区域 330x345 = 113,850 像素中，底色 #FFF7F7 占 82,869（72.8%），
文字主色 #92400E 共 1,957 像素；"蓝色主导"像素 4,158（3.65%），逐个定位后确认全部散布在字形内部，
是 ClearType 次像素抗锯齿的边缘 —— 面板里不存在蓝色背景或蓝字。

（注：本机 CopyFromScreen 抓屏返回整屏纯蓝，故改用 PrintWindow；两者互为独立方法。）

### 14.2 反馈二：报错清单滚轮滚不动、看不到下面内容

根因有两个，都在 v0.2.20 里同时存在：

1. ListBox 默认是"按项滚动"（CanContentScroll=True 且 ScrollUnit=Item）。
   而单条报错的原因很长 —— 实测单行高 396px，视口只有 255px（比视口还高）。
   按项滚动时"滚动一格"的语义失效，滚轮一格都动不了。这就是"滚轮没用"的直接原因。
2. 行内有个 ToolTip（显示路径）。悬停时提示窗弹出会盖住列表并吃掉滚轮事件。

修正：把清单改成像素滚动（VirtualizingPanel.ScrollUnit=Pixel）+ 去掉行内 ToolTip
（路径本来就已经完整显示在行首）。

实测证据（UIA ScrollPattern，不依赖鼠标输入）：
VerticallyScrollable=True，视口占比 91.66%，LargeIncrement 后位置 0% → 100% 且原因文本随之移动，
LargeDecrement 回到 0%（双向可滚）；修好后当前任务最长的那条失败原因已能完整显示（行高 240 ≤ 视口 255）。

### 14.3 反馈三：没有在传文件，网速怎么在跳？

根因：v0.2.19 起网速确实改成了**本机全部活动网卡的 RX+TX 合计**（与任务管理器同源），
但它是"整机流量"，包含浏览器/Windows 更新/Office/其它程序的流量，所以空闲时照样在跳 —— 容易误以为正在传数据。

修正：只在真正传输时显示。判据用"引擎最近 6 秒内是否上报过进度"，因此空闲/暂停/结束后都会自动静默：
显示「—」并清空 60 秒波形。迁移中仍保留两个数字，各有所指：
底栏「网卡实时」= 网卡真实吞吐；迁移页「任务实测」= 本次迁移自己的速率（引擎按落盘字节算）。

实测证据：UIA 空闲态读取底栏为「—」（v0.2.19 时同一位置是 386.89 KB/s）。

### 14.4 反馈四：预计传输时间是不是按实时网速估的？

不是。**预计剩余时间一直按本次任务自己的实测速率估算**：引擎用"已落盘字节 ÷ 用时"得到速率，
再用"剩余字节 ÷ 速率"得出 ETA（见 TransferOrchestrator 的 ProgressSnapshot.EtaSeconds）。
网卡读数只用于显示，不参与 ETA 计算 —— 所以两处数字可能不一致，这是设计如此。

为避免误解，UI 上已明确标注：迁移页卡片标题改为「预计剩余（按任务实测）」，
底栏与卡片都加了 ToolTip 说明"按任务实测速率估算，与网卡实时吞吐无关"。

## 十六、v0.2.25 —— 勾选整盘时的散落文件（真根因）+ 提示栏改名 + 去掉重复状态文字

### 16.1 反馈

### 16.2 根因（不是级联逻辑写错，是变更通知的“名义”写错）

模型层先做了回归测试：把 GUI 真实的 BrowseModels.cs / Helpers.cs 原样编译进控制台测试
（<旧工作区根>\TreeTest），按用户操作顺序驱动——先勾选后展开、先展开后勾选、反向取消、
共享行驱动根节点、半勾后再展开，六个场景全通过。也就是说 **模型值一直是对的**，问题在界面刷新。

真正的原因在 FileRow.SetCheckedSilent：

    public void SetCheckedSilent(bool value) => Set(ref _isChecked, value);

Set() 的参数用了 [CallerMemberName]，取到的是**调用它的方法名**，也就是 "SetCheckedSilent"，
不是 "IsChecked"。于是 PropertyChanged 的名义是 SetCheckedSilent，而 XAML 里复选框绑定的是
IsChecked —— 通知没送到，界面不动。DirNode 的同类方法因为自己显式写了
OnPropertyChanged(nameof(IsChecked)) 所以没受影响：这正是“文件夹勾上了、文件没勾上”的全部原因。

反证（同一份测试里的 OldStyleRow，完全照抄修复前的写法）实测输出：
    “旧写法发出的名字 = SetCheckedSilentOld” —— 即包装方法自己的名字；修复后发出的名字 = IsChecked。

修复：SetCheckedSilent 显式发 IsChecked（顺带补上值相同时提前返回）。
经验：给包装方法做赋值的“静默”通知，必须显式写属性名，不能指望 CallerMemberName。

## 十七、v0.2.26 / v0.2.27 —— 「预检未通过 + 按钮点不动」的两个真根因

### 17.1 反馈

预检未通过；而且预检按钮不让再点，明明数据目录都识别到了。

### 17.2 根因一：预检的 TCP 445 判定被“失效旧 IP”耗光预算（v0.2.26）

现场事实（UIA 读运行中应用）：① 页「IP 或电脑名」填的是电脑名 SRC-PC；目录树里旧电脑 D 盘内容全都列了出来
（说明 SMB 通）；左栏却写着「预检未通过：无法连接 TCP 445」。

独立实测（本机）：
* ping SRC-PC → 解析到 192.0.2.23（SRC-PC.example.invalid）
* .NET Dns.GetHostAddresses(SRC-PC) → 两个地址：192.0.2.125（失效）、192.0.2.23（真身）
* 完全照抄预检代码：TcpClient.ConnectAsync(SRC-PC, 445) 等 5 秒失败；
  ConnectAsync(192.0.2.23, 445) 3 毫秒成功
* 按电脑名访问该共享目录 = 可访问（Windows 重定向器走的是另一条解析/连接路径）

结论：老代码对整台主机只下一个 5 秒总预算，第一个失效地址就把预算耗光 → 误判不可达；
而资源管理器/重定向器能连上 → 出现“目录列得出来、预检却不过”的矛盾。

修复：先把电脑名解析成地址表，逐个地址各给 2 秒短超时，任一通即算通（实测总耗时 2028ms 连上真身）；
并且填的是电脑名时，TCP 探测失败不再直接判死，改由「SMB 凭据会话 + 源路径可读」定论；
填的是 IP 时维持原判（连不上就明确提示）。

真代码验收（CLI 与 GUI 共用同一个 PreflightChecker）：pcmig preflight --host SRC-PC --user user01
--source (该共享) --target <外置测试根> → 显示 SMB 445 端口可达：TCP 445 连接成功（SRC-PC → 192.0.2.23）、
源路径存在且可访问、IPC$ 凭据会话警告（错误 67，对方不导出 IPC$，不阻断）、总体：通过，可以迁移（退出码 0）。

### 17.3 根因二：对话框没有归属窗口，藏在主窗口后面却禁用整个界面（v0.2.27）

排查“按钮点不动”时，枚举运行中进程的顶层窗口，抓到：

    [ControlType.Window] 「PCMig 迁移工具 v0.2.26」 enabled=True 1946x1226
    [ControlType.Window] 「发现未完成的迁移任务」   enabled=True  510x418

主窗口的连接按钮此时是禁用状态。原因是弹出确认框时没有指定 Owner：
Windows 的对话框在不指定 Owner 时会禁用本线程的所有窗口（用户看到的就是“整个界面死了”），
但它不保证显示在主窗口前面——可能落到主窗口背后或另一个显示器上，用户既点不动也不知道关什么。

脚本侧复现：点击「预检并生成计划」「连接并列出共享」时 UIA 抛 ElementNotEnabledException（被那个对话框禁用），
主窗口状态文字也不再刷新。

修复：5 处确认框（更新日志、关闭确认、未完成续传、迁移前提醒、目标盘空间不足）全部补 Owner，
保证对话框一定出现在主窗口正前方并居中；并在弹出「发现未完成的迁移任务」时于左栏提示面板写明该选什么、

## 十九、v0.2.29 对象明细状态不刷新（实测反馈）

**现象**（用户）：迁移进度的「对象明细」表，状态列一直是"待连接"；只有暂停时才变"中断"，
恢复之后仍然是"中断"。

**根因**：进度回调里只在"已完成对象数变化"时刷新表格（比较 CompletedObjects 计数）。
引擎上报"开始对象 X"时完成数不变，所以正在传输的对象永远停在初始值；
暂停时靠回执刷新成"中断"；恢复后对象尚未传完、完成数仍未变，"中断"就一直挂着。

**修法**：新增 ApplyObjectRowStatus，按引擎的逐对象上报实时改行状态：
收到"开始/继续传输"先把遗留的"→ 传输中 / 中断"复位为"待传输"（解决恢复后仍显示中断）；
收到"开始对象 X"把该行置为"→ 传输中"；暂停/中断时把传输中的行置为"中断（可续传）"；
对象完成仍按回执显示完成/有错误/失败。另外把计划对象的初始状态由"待连接"改为"待传输"。

**验证**：
1. 编译通过（0 警告）；
2. 独立复现引擎的消息契约（与本修改所依赖的信号一致，命令行实测输出）：
   开始/继续传输 → 开始对象 object-000001 → 对象 object-000001 Completed（12 B） → 阶段结束: Completed；
3. 代码路径核对：两个进度回调（正常迁移与"尝试修复"）都调用了同一处 ApplyObjectRowStatus。
待用户在下一次真实迁移时做界面确认（界面跑通需要旧电脑凭据，自动化脚本无法可靠输入密码框）。

根因：WriteAtomic 用 `File.Move(tmp, path, overwrite:true)`（MoveFileEx REPLACE_EXISTING）落盘，本机实测**即使读方持有 FILE_SHARE_DELETE 句柄，覆盖改名仍返回 Access is denied**；WriteAtomic 无重试无降级，异常直接终止整个迁移；SaveState(Running) 自身写失败导致状态停在 awaitingReview/running 而进程已退出。

**其他观察（建议，非致命）**：硬杀后阶段停在 running 且无陈旧判定（T05）；杀 robocopy 不自动重试、需人工 resume（T06）；ENOSPC(112) 被判 permanent 且每文件重试 3–33 次（T07）；new/preflight 缺少"源总量 vs 目标剩余空间"前置校验（T01/T07）；文件被占用判 permanent 不重试（T08）；状态损坏时 status 显示 0.0% 容易被脚本误读（T14）；引擎自报速率系统性偏低约 4.6 倍（robocopy 日志滞后瞬时值，T01）；verify --level 2 抽样命中 0 项时应提示"未做内容级校验"（T01）；进度按对象边界成块跳变、超大单对象内会长时间停在同一百分比（T09）；10 万文件产生 45 MB 元数据日志（约 0.85% 传输量，T09）。

### 4（T01-O3）自报速率系统性偏低 —— 回归 3/3 + 交替 A/B

- 复现（v0.3.5）：mid 数据集一轮，自报 243.8 MB/s vs 独立实测 1193.7 MB/s（**4.9 倍**）；

- 根因：自报速度 = 每对象 2 秒瞬时增量的指数滑动平均（0.3×瞬时 + 0.7×旧值），**换对象即重置**——

  → 倍数 **0.99 / 1.00 / 0.99**。

  即偏差从 3.3–4.9 倍降到 ≤1%（同一量级）。

### 2（P0）大文件通道 `/Z` 单线程只有手抄的 1/4 —— A/B 交替各 3 次
- 修复：大文件通道改为 `/MT`（`/J` 仅当源或目标是网络路径时附加，因为本机实测 `/J` 更慢）；
  `/Z` 保留为"可续传优先"备选；新增 `--large-channel auto|restartable|multithreaded`，
  `auto` 首次 `/MT`、同一对象重试第 2 次起自动退回 `/Z`；日志写明本次实际通道。
- 验收（本机 E:，单 6GB 文件与 8×800MB 两种形态，交替各 3 次）：

| 通道 | 6GB 单文件（3 次，MB/s） | 8×800MB（2 次，MB/s） |
|------|--------------------------|------------------------|
| `/Z` | 2087.5 / 1111.1 / 1066.1（均值 1421.6） | 1338.2 / 1261.8 |
| `/MT`（新默认，本机链路） | 2906.3 / 1883.9 / 2030.6（均值 2273.6） | 2275.0 / 2652.4 |
| `/MT + /J`（强制） | 759.4 / 826.1 / 829.3（均值 804.9） | — |

  同一文件交替对比：A2/A3 1066/1111 vs B2/B3 1884/2031 → **快 1.7~1.9 倍**；多文件 **1.8~2.0 倍**；
  强制 `/J` 只有 `/Z` 的 0.57 倍（本地 NVMe 绕过写缓存的代价），故 `/J` 只在网络链路使用。
  6GB 单文件整任务墙钟：`/Z` 3.26/5.85/6.09 s vs `/MT` 2.44/3.62/3.35 s。
- 续传验证（5 次：`/Z` 2 次、`/MT` 2 次、v0.3.7 老二进制 1 次；12GB 文件，kill 后 resume）：
  最终 SHA-256 全部一致；但 **5/5 次都是整文件重传**（续传那一轮写入 98%~100% 的源字节，
  老版本 99.6%）。原因（实测证据）：robocopy `/Z` 会把目标文件预分配到全尺寸——kill 之后目标文件
  已是 12,884,901,888 字节，而实际只写了约 4.1 GB，下一次无法判断已写到哪。
  结论：**断点续传只到"对象级"，是既有行为（v0.3.7 同样如此），本版没有改变它，也未当作卖点**；
  已完成对象不重传、最终数据校验一致这两点仍成立。

## 二十六、v0.3.9 更新日志窗口与报错区易用性修复

**现象（用户实测）**：① 更新日志窗口内点左侧其他版本毫无反应，只能看当前版本；② 左侧显示报错/提示的区域文字超出后无法滚动，内容被裁掉。

**根因**：
1. 列表项模板里的 ContentPresenter 未绑定 HorizontalContentAlignment，整行只有文字那一小块可点中（旧注释"原模板只按内容宽度命中"即为该问题，但当时把 Stretch 设在项上无效）；
2. 报错提示文本 StatusMessage 所在为 Auto 行且无高度上限，随文字无限长高后被窗口裁掉，且没有滚动容器；
3. 列表行点击是否生效在本机无法自动化确认（UIA 枚举该模态窗口失败、模拟点击未落到行上），故按"不依赖命中"的方向重构。

## 二十七、v0.3.10 修复进度去重与口径修正

**现象（用户实测）**：点「尝试修复」时，迁移进度版块里同时出现两条进度条；修复那条显示的数值对不上（不是修复范围），而且固定不动，等于两个总数据摆在那里。

**根因**：
1. 修复卡片与迁移大进度条是**同一版块内的兄弟元素**，修复期间两者同时可见 → 一条变两条；
2. 修复进度的三处绑定沿用了整任务口径：RepairPercent ← s.Percent、RepairText ← CompletedBytes/TotalBytes、RepairObjectText ← CompletedObjects/TotalObjects。这些是**整个任务**的累计值，对修复既不是它的范围，也不会随修复推进而变化 → 观感上就是"两个总数固定摆着"。

**修法**：
- 新增 MigrationProgressVisibility（IsRepairing 时 Collapsed），把「总体进度」大数字与大进度条一起隐藏，同一版块同一时刻只保留一条进度条；
- 修复进度改口径：新增 _repairDone 集合，每次点修复前 Clear()，从引擎消息『对象 X Completed』累计完成数，
  RepairPercent = 完成数 / 修复范围对象数，RepairObjectText = 「已完成 M/N」，
  RepairText = 「本次修复范围 N 个对象 · 当前：<对象或路径>」——随对象完成动态前进；
- 未改动校验/重拷/状态机逻辑；底部常驻进度条按用户意见保留。

**验证**：Release 构建 0 error / 0 warning；三处文档同步（更新日志正文+对照表行、使用说明）；闸门通过；交付哈希比对一致；GUI 自检标题 PCMig 迁移工具 v0.3.10。

**局限（如实记录）**：本机无视觉服务，界面观感需用户实测；修复路径的实机验证需要一个"存在不一致或失败对象"的任务（用事故档案 JOB-20260917-143154-dc9d 之类的留存任务即可触发）。

### 测试中发现并已修复的问题

1. **发版链：源码镜像漏同步顶层文件（本轮实测发现）**
   `tools\release.ps1` 的镜像同步用 `robocopy <项> <项> /E` 逐项复制；当项是**文件**时 robocopy 会把源当目录遍历并报 `ERROR 267 (0x0000010B) Accessing Source Directory …\README.md\`，退出码 16 —— 而原实现不检查退出码，于是 `README.md`、`.gitignore`、`PCMig.sln` 三个顶层文件被**静默漏同步**（首次发版后实测：镜像里的 `README.md` 仍是 v0.5.1 内容）。修法：目录项仍走 robocopy（新增退出码 ≥8 即中止），文件项改走 `Copy-Item -Force` 并校验，dry-run（`/L`）逐项留证；随后复跑核对为「不一致 0、缺失 0」。
2. **发版链：`<InformationalVersion>` 无写入点**
   v0.5.3 前脚本完全不处理该节点，而它决定「关于」页、文件元数据与 `pcmig --version`。补入四个工程的 Patch 与声明式自查（各工程必须恰好一处且等于目标版本，不得带 `Preview` 后缀），并在自检中回读 `FileVersion=0.5.3.0`。
3. **发版链：启动自检只打印不校验**
   原自检只确认进程未退出。现增加文件元数据断言（FileVersion/ProductVersion 必须匹配目标版本、不得含 `preview`）与**窗口标题断言**（必须等于 `PCMig 迁移工具 · v0.5.3`），实测标题一致。
4. **回执文件名同秒碰撞（潜在风险，已最小修复）**
   回执文件名原为 `<对象ID>-<yyyyMMddHHmmss>.json`，同一对象在同一秒内两次落盘会互相覆盖。修法：同名时追加 `-1`…`-99` 后缀（有界），并补 4 条针对性用例（同秒两次、同秒三次、后缀不污染对象身份、历史命名仍可读）。
5. **报告不得作未经验证的绝对保证**
   报告中「数据没有丢」类措辞与导出路径的脱敏一致性被独立复核；现改为只陈述回执与日志事实（「本报告未做数据一致性核对，请再点『验证』」），页脚明确「不代替验证的数据一致性结论」。
6. **公开源码不得带机器内部证据**
   本轮新增的两个测试文件里出现了真机名与实验账号字样（追踪文件中命中 0 处 ⇒ 会成为首次公开）。已改为占位名并复跑定向用例。
7. **未完成对象的报告口径**
   `Interrupted` 原被排除在「未完成」结论之外 ⇒ 报告会整段漏掉被中断的对象。现纳入未完成口径；真机作业里 object-000003 的「先中断后完成」两趟回执并列展示，对象明细按最新一趟显示为完成。
