## 二、本轮**证伪**：`PrevStepButton.IsEnabled` 不是 P0 关闭崩溃的根因

### 线索来源（重要：项目里早有一条我没注意到的记录）
`docs\工作交接-20260927-四页Shell与DesktopAcrylic材质体系与开发者调节器.md:45-58` 记录了上一会话的**二分法实验链**：

| 实验（同一构建、正常 Alt+F4 关闭） | 结果 |
|---|---|
| 不切页 + 关闭 / 切 Step2 / 切 Step3 + 关闭 | 退出码 0，**0 崩溃** |
| **切 Step4 + 关闭** | **0xC000027B，1 崩溃** |
| 访问过 Step4 → 回 Step1/Step3 → 关闭 | 仍崩 |
| Step4 内容全 Collapsed / 只留标题 / CheckBox 换掉 | 仍崩 |
| 按 Ctrl+4 但 Step4 页根本不显示 | 仍崩（⇒ 与页面内容无关） |
| **去掉「把『下一步』按钮置灰」这一行** | **退出码 0，0 崩溃** ✅ |

**已确认根因**：运行期把带自定义 `ControlTemplate`（含 `ThemeShadow` + `Translation` 的 Disabled VisualState）的按钮
`IsEnabled=false`，会在**窗口关闭时**触发 WinRT 类激活失败。
**当时的修法**：Step4 是最后一步 → 改为**隐藏**「下一步」（`Visibility`）。

### 我顺着这条线索提出的假设与检验
`grep 'IsEnabled\s*='` 全项目**只剩一处**：
```
MainWindow.xaml.cs:196   PrevStepButton.IsEnabled = Nav.Current != StepKind.Connect;
```
⇒ 假设：「下一步」改成了 `Visibility`，但**「上一步」仍是 `IsEnabled` 置灰**，是同一模式的残留。

### 检验方法（只读 XAML 核查）
比对两个按钮模板的 `Disabled` VisualState：

| 按钮 | 样式 | Disabled 状态里的 Target |
|---|---|---|
| `NextStepButton` | `PCMigPrimaryButton` | `Root.Background` / `Root.BorderBrush` / `TopSheen.Opacity` / `LabelNormal.Visibility` / `LabelDisabled.Visibility` —— **且 `PointerOver`/`Pressed` 含 `Root.Translation`** |
| `PrevStepButton` | `PCMigSecondaryButton` | 仅 `Root.Background` / `Root.BorderBrush` / `Presenter.Foreground` —— **完全不含 `Translation`、不含 `Shadow`** |

### 结论：**假设被证伪**
历史崩溃的机制是「**含 `Translation` setter 的 Disabled 状态**」。
`PCMigSecondaryButton` 的 Disabled 状态里**没有任何 `Translation` / `Shadow` setter**，
因此 `PrevStepButton.IsEnabled` 这条路**与历史崩溃机制不符**。

**⇒ 不能把 L196 当作 P0 根因。** 本轮**没有改任何代码**。

> 记录这条是因为它有独立价值：它把「置灰按钮导致关闭崩溃」这个已知族**限定在含 `Translation` setter 的模板**上，
> 为后续排查缩小了范围。

## 四、本轮查证到的其他事实（保留证据）

### 4.1 `PCMigPrimaryButton` 的 `TopSheen` 层级（P5 根因，只读核查）
`Themes\Controls.xaml:49` 的模板结构：
```
<Border x:Name="Root" Background="{TemplateBinding Background}" CornerRadius="12"
        BorderBrush="#86FFFFFF" BorderThickness="1"
        Padding="{TemplateBinding Padding}"        <!-- = 20,12 -->
        Translation="0,0,5" Shadow="{StaticResource ElevationMedium}">
  <Grid>
    <Border x:Name="TopSheen" Height="16" VerticalAlignment="Top" .../>   <!-- 16px 白色渐变 -->
```
**`TopSheen` 位于 `Root` 的 `Padding` 之内**，而 `Root` 自身又带 1px 白色描边。
⇒ 用户「外面一个框、里面还有一个高光」的描述与源码结构完全对应。
**只改颜色或高度无效，必须动模板层级。**

### 4.2 开发者面板按钮裁切（A2，三条独立证据）
1. **源码算术**：`Width="348"` + `Padding="16"` ⇒ 内容 316 DIP；横向 `StackPanel`（**不换行**）四按钮 ≈374 DIP ⇒ **溢出 58 DIP**。

3. **XBF 产物**：UTF-16 串「导出 JSON」存在、「导出 JSC」不存在 ⇒ **源码正确，是渲染被裁切**。

**附带更正**：归档截图 `p-devpanel.png` 与 `p-updatelog.png` **文件名与内容互换**（前者实为「更新日志」面板）


对照：异常码 `c0000005` 一致；`AV.Fault=Read` 一致；`NullPtr` 一致；`+0x58` 语义一致；
发生时点（进程退出 / DLL 卸载）一致。

**机制**（issue 原文）：
> calling into `threadpoolwinrt.dll` when it is already freed. On process shutdown, dlls are unloaded in reverse load order...

**框架方自述修复方向**：
> The most obvious fix would be **not calling `ThreadPoolService::ReleaseFactories` if deinitialization happens due to process exiting.**

**独立佐证链**：`0x7F9880` 经 PE 解析**落在 `Microsoft.UI.Xaml.dll` 的 `.text` 段内**
（VA `0x1000` / VSize `0xA075EF`，可执行）；关闭期该 DLL 唯一会执行的自有代码就是它的 `DllMain`
⇒ 只能是 `DllMain → DeinitializeDll → ReleaseFactories`。
这与"**零交互启动也崩**""**与页面内容无关**"（上一会话已二分证明）**完全相容**。

**对比上一会话另一崩溃族**（`Windows.ApplicationModel.LimitedAccessFeatures` / `0xC000027B`）：
**本轮这个不是它**，不要用"置灰按钮"那条已修结论来解释本崩溃。

### B.3 版本事实 —— **纠正我此前一处不准确表述**

| 项 | 实测值 |
|---|---|
| `Microsoft.UI.Xaml.dll` 文件版本 | **`3.2.3.2609`** |
| 该 DLL **产品版本** | **`2.3`**（产品名 `Windows App SDK`） |
| csproj `PackageReference` | `Microsoft.WindowsAppSDK` **`2.5.1`** |
| 我此前写的"Windows App SDK 2.5.1" | **不准确**：那是 nuget 引用版本，**实际框架二进制在 2.3 线** |

issue #7260 的 milestone 是 WinAppSDK **1.3**，而我们跑 **`3.2.3.2609`** —— **远新于**该 milestone
⇒ **本崩溃在新版本上依然存在（或同族未修变体）** ⇒ **升级版本解决不了**。

### B.4 排除的资料（避免误用）
- Medium「Fixing C# WinUI 3 Crashes When Upgrading to .NET 8」讲的是 **`0xc0000374` 堆损坏**，
  与我们的 `0xC0000005` **不同族** ⇒ **已弃用，不采信其结论**。
- WinAppSDK 1.3 release notes 里「crash when the app was closed because XAML shut itself down too early」
  属**同症状族但非同一 issue**，仅作旁证。

### B.5 结论与待授权方向

**这是 Windows App SDK 的框架级缺陷，不是 PCMig 的源码缺陷。**
因此我此前给用户的"二分法改代码 / 装 WinDbg"两条路**都不是必需的了**；取而代之：

| # | 方向 | 风险 | 需授权 |
|---|---|---|---|
| 1 | 关闭时先清理 thread-pool 支持的 WinRT 对象（`MotionState.cs` 的 `DispatcherQueueTimer` 字典 —— 该类 102 行**无 `Dispose`**） | 低 | 是 |
| 2 | 关闭路径显式结束进程（`Environment.Exit(0)`）绕开 Xaml 卸载 | 中（可能只把崩溃点后移，**必须实测 WER 增量**） | 是 |
| 3 | 接受为已知平台缺陷并在交付说明如实披露（**WER 清洁闭环不达标**） | 无 | 是 |
| 4 | 装完整转储（WER `LocalDumps\DumpType=2`）复现以**确证**谓词 | 需系统级改动 | 是 |

**候选触发源（不主张因果）**：`MotionState.cs:23/60-69/78`（`DispatcherQueueTimer`）、
`BackdropSpike.cs:238-240/287-291`（`TryEnqueue` + `Task.Delay`）。

### B.6 转储里拿不到的东西（如实说明）
| 想要 | 状态 | 原因 |
|---|---|---|
| 寄存器 / 崩溃线程栈 | **拿不到** | `ThreadContext` 指向的段**前 256 字节全零**（实测非零字节 = 0） |
