## 二、【P0】关闭崩溃 —— 已修复（应用侧规避）

### 2.1 最终修法（两处）

**`src\PCMig.WinUI\MainWindow.xaml.cs`** —— 关闭路由改为更早的 `AppWindow.Closing`：

```csharp
AppWindow.Closing += (_, args) =>
{
    args.Cancel = true;      // 不交给框架的关闭流程
    ShutdownAndExit();
};

private void ShutdownAndExit()
{
    if (_shuttingDown) return;
    _shuttingDown = true;
    try { MotionState.Current.Dispose(); } catch { }
    try { ViewModel.Dispose(); } catch { }
    Environment.Exit(0);
}
```

**`src\PCMig.WinUI\Presentation\MotionState.cs`** —— 新增 `Dispose()`：停止并释放全部
`DispatcherQueueTimer`；同时把定时器回调改为**自带 timer 引用**（不再依赖字典查找，
字典清空后仍能 `Stop()`）。并加 `_disposed` 守卫，关闭后不再创建新定时器。

### 2.2 为什么必须用 `AppWindow.Closing` 而不是 `Window.Closed`

`Closed` 触发时 `Window.Close()` 已开始拆卸 XAML，时机偏晚（实测仍崩）。
`Closing` 更早，取消默认关闭后由本进程主动 `Exit`，绕开
`ntdll!LdrShutdownProcess → Microsoft.UI.Xaml.dll!DllMain(DLL_PROCESS_DETACH)`
这条会命中已卸载模块的路径。

### 2.3 根因（转储级证据，8/8 指纹一致）

| 项 | 值 |
|---|---|
| 异常码 | `0xC0000005`（访问冲突） |
| 读/写 | **读**（`ExceptionInformation[0]=0`） |
| 失败地址 | **`0x58`** ⇒ NULL 基址 + `0x58` 字段 |
| 故障模块 | `Microsoft.UI.Xaml.dll` |
| **模块内偏移** | **`0x7F9880`（固定，跨 8 个转储、多个 ASLR 基址、跨 7 小时）** |

`0x7F9880` 经 PE 解析落在该 DLL 的 `.text` 段内（VA `0x1000` / VSize `0xA075EF`，可执行）。
关闭期该 DLL 唯一会执行的自有代码就是它自己的 `DllMain`。

联网检索命中同族已知缺陷 [microsoft-ui-xaml #7260](https://github.com/microsoft/microsoft-ui-xaml/issues/7260)，
其 WinDbg 栈逐项吻合：

```
threadpoolwinrt!...ActivationFactory<...IThreadPoolStatics...>::Release+0x58   ← 读 NULL
Microsoft_UI_Xaml!ThreadPoolService::ReleaseFactories+0x8b
Microsoft_UI_Xaml!DeinitializeDll+0x62
Microsoft_UI_Xaml!DllMain+0x39
ntdll!LdrShutdownProcess → RtlExitUserProcess → ExitProcessImplementation
```

> 该 issue 的原文：calling into `threadpoolwinrt.dll` when it is already freed. On process
> shutdown, dlls are unloaded in reverse load order... The most obvious fix would be **not calling
> `ThreadPoolService::ReleaseFactories` if deinitialization happens due to process exiting.**

**结论：这是 Windows App SDK 的框架级缺陷，不是 PCMig 的源码缺陷。**

### 2.4 版本事实（纠正早前不准确表述）

| 项 | 实测值 |
|---|---|
| `Microsoft.UI.Xaml.dll` 文件版本 | **`3.2.3.2609`** |
| 该 DLL **产品版本** | **`2.3`** |
| csproj `PackageReference` | `Microsoft.WindowsAppSDK` **`2.5.1`** |

早前说"用的是 2.5.1"**不准确** —— 那是 nuget 引用版本；**实际框架二进制在 2.3 线**。
issue #7260 的 milestone 是 WinAppSDK **1.3**，我们跑 `3.2.3.2609`，**远新于它**
⇒ **升级版本解决不了本崩溃**。

### 2.6 被证伪的方向（如实记录，避免重复尝试）

**方向 1「只释放应用持有的定时器」单独验证：无效。**

只加 `MotionState.Dispose()`、不改关闭路由时：退出仍 3081 ms、退出码仍 `0xC0000005`、
新增转储，且**新转储指纹与修复前逐项一致**（`+0x7F9880` / 读 / `0x58`）。

⇒ 触发源**不是**应用持有的 `DispatcherQueueTimer`；那些 thread-pool 工厂是**框架自身缓存**的
（零交互启动亦崩，早已证明）。`MotionState.Dispose()` 作为资源泄漏治理保留（真实改善），
但**不解决**关闭崩溃；真正生效的是 `Environment.Exit(0)`。

## 四、本轮我在测量方法上犯的错误（**必读，防止后续会话重蹈**）

我一度得出**错误结论**"视觉改动没有生效"，并为此浪费了大量验证轮次。真因**全部在我的测量方法**，
不在代码。逐条记录：

1. **假设客户端原点等于截图原点。** 实测窗口每次启动落在**不同屏幕位置**
   （本次会话观测到 `(26,26)`、`(52,52)`、`(130,130)`、`(156,156)`、`(182,182)`、`(208,208)`），
   而 `ClientToScreen` 显示客户端左上在截图内的偏移是 `(8,0)` 一类的**非常数**。
   任何写死偏移的采样都会采到空白，从而"证明"改动未生效。

2. **把侧栏步骤徽章误当成页标题徽章。** 侧栏 rail 宽约 **336 DIP**，其自身徽章位于
   `x≈344..375, y≈63..86`（截图坐标）；而**页标题徽章**在其下方约 46 DIP 处。
   我先前用"x≥300 即内容区"的假设，采到的正是**侧栏徽章**——它本来就没被我改动，
   于是"新旧逐像素完全相同"看起来像是改动失效。

3. **`System.Windows.Forms.SendKeys` 未加载时静默失败。** 一次探针里
   `Add-Type -AssemblyName System.Windows.Forms` 缺失，`SendKeys` 抛
   `Unable to find type`，导致**切页根本没发生**，四张"不同页面"的截图其实是同一页。
   后续在验收脚本中已加 `Add-Type` 并改为**先证明切页成功再信任该帧**。

4. **解析 MINIDUMP / GIF / 位运算的历史错误（沿用早前记录）**：
   `([byte]2 -shl 8)=0`（按操作数宽度截断，必须用 `[int]`）；
   GIF 编码器漏写 LZW 最小码长字节；用 `0x2C` 出现次数推断 GIF 帧数（压缩数据近似随机，无效）。

5. **`write` 工具会剥掉 UTF-8 BOM** ⇒ PS 5.1 把带中文注释的 `.ps1` 当 ANSI 读并**重写正文**，
   造成不可复现的偏移错误。**诊断脚本一律纯 ASCII**；必须带 BOM 的脚本写完要**复查前三字节**。

6. **路径前缀错误（重复犯）**：`archive\` 在**工作区根** `<工作区根>\archive\`，
   **不在** `PCMig\` 下。本轮又误把证据日志写到 `PCMig\archive\evidence\`（该目录不存在，写入失败）。

7. **测试工具自身污染证据**：早前一版验证脚本用 `WaitForExit(3500)`，3.5 秒未退出便**强杀**，
   强杀产生的 `0xC0000005` 与"关窗崩溃"信号**无法区分**，且 WER 统计被前后轮重叠污染。
   已改为 **20 秒超时 + 绝不强杀**。

**当前 WER/转储计数的诚实说明**：本会话 WER 由 **111 增至 121**、转储由 **6 增至 8**。
其中包含：(a) 修复前的**故意复现**；(b) 我**有缺陷的强杀测试脚本**造成的 2 次
（增益轮次退出码为 `0xFFFFFFFF`，即被强杀），**不是应用缺陷**。
修复生效后连续 3 次关闭的增量为 **0**。
