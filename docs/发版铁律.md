**铁律 2**　**交付区 = `<交付区>`。** 一切对外交付物只放这里。

**铁律 3**　**工作副本 = `<发版工作副本>`。** 用于安装态自检启动（脚本会自动创建，无需预装）。

## 第三部分 · 发版流水线（缺一项就打不出包）

**铁律 12**　**先写日志，再打包。** 没写日志就打不出包——这是设计，不是意外。

**铁律 13**　发版前**三处**必须已写好本版内容（脚本硬校验，缺一项中止）：
1. `docs/更新日志.md` —— 顶部「版本号与发布日期对照」表**加一行**；正文**按新到旧插入** `## vX.Y.Z — 主题` 一节，写清 **背景 / 改了什么 / 为什么（根因）**，面向使用者、不含内部隐私。
2. `docs/使用说明.txt` —— 顶部新增一段 `■ vX.Y.Z …`（用户视角：这一版对他意味着什么）。
3. 版本号全部一致（脚本自动改 + 声明式自查）：**四个 csproj**（`PCMig.Cli` / `PCMig.Core` / `PCMig.Gui` / **`PCMig.WinUI`**）、**两个窗口标题**（`src/PCMig.Gui/MainWindow.xaml` 的 `Title="PCMig 迁移工具 vX.Y.Z"` 与 `src/PCMig.WinUI/MainWindow.xaml` 的 `Title="PCMig 迁移工具 · vX.Y.Z"`，注意 WinUI 标题多一个 `·`）、**WinUI 主界面里两处运行时可见的版本徽章**（`src/PCMig.WinUI/MainWindow.xaml` 的 `Text="vX.Y.Z"`：① 标题栏右侧 `TitleBarVersionText`，② 标题行「更新日志」徽章内的 TextBlock）、`README.md`、`installer/pcmig.iss`（`MyAppVersion` 与 `VersionInfoVersion`）。
   ⚠ **v0.5.1（2026-10-06）补漏**：那两处 `Text="vX.Y.Z"` 徽章在 v0.5.0 时**没有被脚本覆盖**（脚本只改了窗口 `Title`），结果是窗口标题已是新版、界面上的徽章还显示 v0.5.0。`TitleBarVersionText` 虽有 `x:Name`，但**没有任何 `.cs` 给它赋值**，所以 XAML 字面量就是运行时真值 ⇒ 必须由脚本替换。脚本现在按正则 `Text="v[0-9.]+"` 一并替换这两处（实测恰好命中 2 处，不会误伤「更新日志」按钮 ToolTip 里的「从 v0.1.0 起」），并追加一条**反向自查**：该文件里所有 `Text="v<数字>"` 必须**全部**等于目标版本，否则中止。
   ⚠ 版本号统一是**源码树口径**：`src/PCMig.Gui`（旧 WPF）仍留在仓库里、仍随源码树一起改版本号，但**不再进入正式用户交付物**（见铁律 13-A）。
   ⚠ `PCMig.WinUI.csproj` 原本没有 `<Version>` 节点，v0.5.0 起由脚本写入；若该节点被删除，闸门会因声明式自查失败而中止（属于设计，不要绕过）。

**铁律 13-A（v0.5.1 起 · 唯一 WinUI 主前端）**　**产品主界面是 WinUI 3（`PCMig.WinUI`），发版链必须发布它**：
`tools/release.ps1` 必须 `dotnet publish src/PCMig.WinUI/PCMig.WinUI.csproj -c Release -r win-x64 --self-contained true -p:Platform=x64 -o dist/winui`，并把 `dist/winui` **整棵目录树**铺进 `dist/app`（WinUI 是 unpackaged + WindowsAppSDK/Win2D 自包含应用，原生组件必须与 exe 同目录 ⇒ **不能压成单文件**）。

**★ v0.5.1（2026-10-06）起 · 旧 WPF 前端退出正式发布物 ★**
- **正式用户交付物只允许两个可执行文件**：`PCMig.WinUI.exe` 与 `pcmig-cli.exe`。
- 旧 WPF 前端（`src/PCMig.Gui`）**源码继续保留在仓库里**作为历史实现与回退参考，但**不得再进入正式用户交付链**：不 publish、不进 `dist/app`、不进 `Portable`、不进安装目录、不进开始菜单、不进安装完成自检、不进 SHA256 清单。
- **不允许**再以「备用」「经典界面」「回退」任何名义把旧 WPF 可执行文件随安装包或 Portable 一起发布。
- `tools/release.ps1` 里对 `dist/app`、`Portable`、工作副本 `<发版工作副本>` **三处**都有硬门禁：一旦出现 `PCMig-classic.exe` 或 `PCMig.exe` 立即 `Abort` 中止发版。
- `installer/pcmig.iss` 不再有 `PCMig-classic.exe` 的 `[Icons]` / `[Run]` 条目；安装器图标也不从 WPF 工程目录取（改为 `installer/pcmig.ico`）。
- **v0.5.0 及以前的历史安装包保持原样、不回改**；v0.5.0 与 v0.5.1 作为两个独立正式版本**并列保留**。
- 任何情况下都不得只打旧 GUI 而把 WinUI 留在仓库里——那等于发出去的版本与「WinUI 3 全新界面」的主题不符。

**铁律 14**　**发版必须走脚本，禁止手工打包**：
```
powershell -NoProfile -ExecutionPolicy Bypass -File "<仓库根>\tools\release.ps1" -Version 0.4.2
```

**铁律 15**　脚本的**五道闸门**必须全绿，任何一道红都不许绕过：
① 更新日志正文有条目 → ② 版本对照表有一行 → ③ 使用说明有段落 → ④ 交付区无同名安装包（拒绝同版本覆盖）→ ⑤ 仓库无真实口令残留。

**铁律 16**　**一个版本号只发一次。** 脚本拒绝同版本覆盖；需要精修就**顺延版本号**（v0.4.0 上午已发 → 精修版顺延为 v0.4.1，即此例）。

**铁律 17**　**跳号必须写清原因**，并记进更新日志。

## 第四部分 · 交付物（四件套 + 逐文件哈希）

**铁律 18**　交付**四件套**，缺一不算交付成功：
1. 安装包 `<旧镜像交付区>\PCMigSetup-<版本>.exe`
2. 便携版 `<旧镜像交付区>\Portable\`（v0.5.0 起是 **WinUI 整棵目录树**：`PCMig.WinUI.exe` + 其原生组件、`pcmig-cli.exe`、`matrix\migration-matrix.yaml`、`使用说明.txt`、`更新日志.txt`、`首日实测检查表.md`）。Portable 与工作副本 `<发版工作副本>\` 都必须是**整棵 app 树**，只拷 exe 会让 WinUI 起不来。
   ⚠ **v0.5.1（2026-10-06）起不含 `PCMig-classic.exe`**：旧 WPF 前端退出正式交付链（见铁律 13-A）。
3. 记事本可直接打开的 `<旧镜像交付区>\更新日志.txt`（**UTF-8 带 BOM + CRLF**，内容与 md 同源）
4. 工作副本 `<发版工作副本>\`

**铁律 19**　**逐文件 SHA256 比对全部 MATCH 才算交付成功**（v0.5.1 起：`PCMig.WinUI.exe` 两处、`pcmig-cli.exe` 两处、安装包、`更新日志.txt`、`使用说明.txt`，共 **7 组**）。不一致立即中止。
　　⚠ v0.5.0 及以前是 9 组（多出 `PCMig-classic.exe` 两处）；旧 WPF 前端退出交付链后这两组同步删除。

**铁律 20**　交付区按「**各版本并列存放**」使用：`PCMigSetup-*.exe` **历史安装包一律全量保留，脚本绝不删除**（脚本只打印并列版本清单）。`使用说明.txt` / `更新日志.txt` 以 `Portable\` 内为准同步到交付区根。
　　⚠ **v0.5.1（2026-10-06）修正**：本条原写作「交付区只保留最新安装包，旧包由脚本清理」，与磁盘事实（交付区并列 14 个历史包）和用户明确要求（v0.5.0 与 v0.5.1 作为两个独立正式版本并列保留）直接矛盾。历史上曾因自动清理删掉交付区 4 个历史包，后经逐文件 SHA256 校验恢复 ⇒ 本条按事实改正为「全量保留」。

## 第五部分 · 发版后三验（不接受"看起来没问题"）

**铁律 20-A（v0.5.0 起）**　**冷启动与四步可用性验证**：启动**新构建**的 WinUI 主界面，确认标题/badge/版本信息确实是本版；并确认 Step1 / Step2 / Step3 / Step4 四页都能打开、无 XAML 资源错误、无启动 Crash。这是 WinUI 成为主界面后新增的最低门槛（旧 WPF 时代靠窗口标题即可，不足以覆盖 WinUI 的资源与 WindowsAppSDK 依赖问题）。

**铁律 21**　三处入口都必须能看到本版：
1. 应用内顶栏「更新日志」——**本版条目在最上方且默认选中**；
2. 记事本打开 `<旧镜像交付区>\更新日志.txt` 与 `<旧镜像交付区>\Portable\更新日志.txt`——含本版；
3. 命令行 `pcmig changelog`——输出含本版。

**铁律 22**　涉及勾选/计划/传输逻辑的改动，先跑 `<旧镜像根>\TreeTest` 模型级回归（直接编译 GUI 真实源码文件）。

**铁律 23**　本轮**根因 / 修法 / 验证方式**必须追加进 `docs/测试报告-公司环境.md`，缺这一条不算完工。

## 第六部分 · 质量证据（没有证据＝没修）

**铁律 24**　每次改动至少**两类独立证据**（互相不能是同一个读数）：
- **复现证据**：改之前能稳定复现（脚本 / UIA 读数 / 日志行 / 哈希值 其一）；
- **修好证据**：改之后同一条路走通，且**换另一种方法**再确认一遍。

**铁律 25**　故障类问题：**连续复现 3 次、修复后连续回归 3 次**，且**正常路径不退化**，才算修好。异常只出现一次不算复现，修一次没回归不算修好。

**铁律 26**　涉及数据正确性的改动，必须跑 `tools/stability-test.ps1`（逐文件 SHA256 三方核对：自写脚本 + 应用自带 verify + robocopy 清单）。

**铁律 27**　**验收判据是数据，不是"成功"二字**：文件数、总字节、抽样/全量 SHA256 逐项对齐。

## 第七部分 · 编码与实现禁区（血泪换来的）

**铁律 28**　**所有 `.ps1` 必须 UTF-8 带 BOM。** PS 5.1 读无 BOM 的 UTF-8 脚本会按 GBK 解析中文 → 字符串与引号配对错乱 → 脚本直接坏掉。**编辑工具保存后必须复查前三字节 `EF BB BF`**（本文件修订当日就因编辑丢失 BOM 触发过一次，已修复）。

**铁律 29**　**禁止用"注释掉语句"的方式做批量替换**（v0.3.7 事故：三行被接成一条 lambda 链，编译通过但语义全毁，窗口从未显示）。替换后必须人工复核语义。

**铁律 30**　**XAML**：隐式 Style **只改不新建**（重复会报 `Item has already been added` → 启动 XamlParseException）；Property Element（如 `Grid.RowDefinitions`）位置必须合法（否则 MC3088）；改完启动必须无黑屏、无 XamlParseException。

**铁律 31**　**验证必须跑"刚 Build 出来的新 EXE"**，禁止拿旧的 `win-x64` publish 产物顶包；验证前核对时间戳。

**铁律 32**　**截图必须先定位 PCMig 真实窗口**，禁止抓到浏览器/其它前置窗口当结论。

**铁律 33**　PowerShell 中 `@(...)` 里**逗号优先级高于 `+`**，`'a' + $x + 'b'` 会被拆成多元素；改 `installer\pcmig.iss` 版本号必须用**正则或整行替换**，改完自查。

**铁律 34**　WPF `Set(ref _field, value)` 的 `[CallerMemberName]` 取的是**调用它的方法名**；包装方法（如 `SetCheckedSilent`）里必须显式 `OnPropertyChanged(nameof(IsChecked))`。

## 第八部分 · 视觉与"看不见"的改动

**铁律 35**　**看不见的东西不改。** 开发侧无视觉能力时做 UI 改版＝反复返工（v0.3.1~3.3 三轮全退）。UI 改动必须走闭环：**修改 → 编译 → 启动 → `tools/uishot.ps1` 截图 → 用视觉模型自查截图 → 通过才进下一阶段**。

**铁律 36**　视觉改动范围**锁死在 Theme / Style / 模板层**，业务零改动（v0.4.0 / v0.4.1 均遵守：仅 XAML + 资源字典 + 纯 UI 初始化）。

**铁律 37**　**回退通道必须常备**：出现任何视觉异常，先设环境变量 `PCMIG_CLASSIC_UI=1`（或 exe 旁放 `classic-ui.flag`）切经典主题，判断是否新视觉引入，再定位。
　　⚠ **v0.5.1（2026-10-06）范围澄清**：这条回退**属 WPF 源码内的能力**（实现在 `src/PCMig.Gui/App.xaml.cs`，且有契约测试 `tests/PCMig.Core.Tests/V5PresentationContractTests.cs` 断言该源码仍在位）。从 v0.5.1 起**正式交付物里不再提供旧 WPF 前端**（见铁律 13-A），所以该回退**不再是"随包可选前端"**——需要时从源码树自行 build `src/PCMig.Gui` 作为回退参考。本条的其余部分（用它切经典主题以定位视觉异常）对**仓库内开发调试**仍然有效。

**铁律 38**　**如实记录遗漏**。做不到的（如未实测高 DPI、网速着色跳过、续传只到对象级）必须写进更新日志与测试报告的"已知遗漏/限制"，**不许瞒**。

## 第九部分 · 安全与凭据

**铁律 39**　**真实口令绝不进交付物、绝不进仓库。** 发版脚本第 5 道闸门会全仓扫描（`.ps1/.py/.md/.txt/.cs/.xaml/.iss/.json/.yaml`，排除 `bin|obj|dist`）；命中即中止，示例一律写 `<口令>`。push 到 GitHub 前同样适用。

**铁律 40**　交付文档提及凭据一律用**"见某处"引用**，不复制明文。

## 第十一部分 · 备份纪律（任何关键改动之前）

> 立此部分的直接原因：本项目在 v0.4.5 之后引入测试基础设施时，用户明确要求
> "任何要做关键改动的行为，之前都要进行备份以方便回档"。此前项目只有"发版时由脚本做镜像"
> 一种备份时机，**改代码之前没有回档点**——这是流程上的真实缺口。

**铁律 43**　**改工作区文件之前，先备份。** 任何"关键改动"——包括但不限于：改业务代码、改发版脚本、改主题/样式/设计 Token、批量替换、结构性重构、引入测试框架、改版本号、动 `.sln`/`.csproj`——**动手前必须完成备份**。不允许"先改了再说""反正改动很小"。

**铁律 44**　**备份必须三重，且每一重都要当场验证"真的能回档"。**

| 重 | 形式 | 位置 | 验证方式（必做） |
|---|---|---|---|
| 1 | git tag | 本仓库 | `git rev-parse <tag>^{commit}` 解析出预期 commit |
| 2 | 源码镜像 | `<旧镜像根>\<PCMig-描述-日期>` | 关键文件与源文件逐一 SHA256 **MATCH** |
| 3 | git bundle | `<旧镜像根>\PCMig-<版本>-<描述>.bundle` | `git bundle verify` 通过，refs 数量对得上 |

镜像用 `robocopy /E`，**排除 `bin` / `obj` / `.git` / `dist` / `.vs`**。

**铁律 45**　**备份清单必须落盘。** 每次关键改动前生成 `<镜像>-清单.md`，写明：备份时间、源仓库路径、**HEAD 完整 SHA**、tag 名、bundle 路径、关键文件 SHA256。
**没有清单的备份等于没备份**——回档时不知道该回到哪个 commit。

**铁律 46**　**回档手段必须与备份同时写清**（写进清单里）：

```powershell
git checkout <tag> -- src/                          # 只回源码
git stash                                           # 暂存当前未提交改动（不丢）
robocopy "<镜像目录>" "<旧镜像根>\PCMig" /E    # 整目录覆盖
git clone "<bundle文件>" <目标目录>                   # 从 bundle 重建完整仓库
```

**铁律 47**　**tag 命名约定，且发布 tag 永不移动。**
- 改动**前**的基线：`<当前版本>-before-<描述>`（例：`v0.4.5-before-tests`）
- 改动**完成并验证通过后**：`<当前版本>-<描述>`（例：`v0.4.5-tests`）
- **发布 tag（如 `v0.4.5`）是交付物的身份，永不移动、永不覆盖**——它不是工作进度书签。

**铁律 48**　**备份未完成，不许动手。** 若备份任一项失败（镜像不完整、bundle verify 不过、SHA256 不 MATCH），**先解决备份问题**，不许"先改着，备份回头补"。

## 第十二部分 · 交接与历史连续性

**铁律 49**　**交接必须新建档案，历史永久保留。** 用户要求交接时，**必须新建**（不得覆盖、不得替换既有文件）`docs\工作交接-YYYYMMDD-主题.md`：`YYYYMMDD` 取交接当日日期，`主题` 用短词概括本次交接内容；若当日已存在同名文件，主题后顺延 `-2`、`-3`…，**任何历史交接文档一律永久保留，禁止删除、覆盖、改名**。

交接文档**至少**须包含以下八项，缺一项不得视为交接完成：
1. **本会话完成事项**——逐条列明做了什么、根因是什么、结论是什么；
2. **权威路径 / 版本 / 工作树状态**——权威工作区绝对路径、当前版本、HEAD 完整 SHA、未提交改动清单、tag / branch 状态；
3. **已改文件**——逐文件绝对路径 + 一句改动说明；
4. **测试与证据**——两类独立证据位置、故障类 3 复现 + 3 回归结果、截图 / 日志 / 哈希等证据；
5. **发版与哈希 / 三验**——若本会话发版：版本号、交付四件套路径、逐文件 SHA256 结论、发版后三验结果；
6. **备份与回退**——三重备份清单 / tag / bundle 位置与回退命令；
7. **已知限制 / 风险**——没测到、没做到、接班人动手前必须知道的；
8. **下一会话待办与建议命令**——可照抄执行的待办与命令序列。

**凭据只引用，不记录明文。** 交接文档提及任何口令 / 凭据时只写"见某处"（凭据保管位置），**绝不写入明文**，也不写其他可还原的占位格式。

**未写交接文档，不得声称完成交接。** 用户要求交接而文档未落盘、八项缺项、或含明文凭据的，一律视为**交接未完成**；补齐之后才可宣称"已交接"。

## 第十三部分 · AI 协作分工（主控规划与验收）

**铁律 50**　**能用子模型（子代理）就优先用子模型；主控只负责规划、授权边界与验收，并对最终结果负全责。**

凡是可以**安全、有效**地由子模型 / 子代理独立承担的确定性工作——包括但不限于：独立审计与只读取证、备份与镜像 / bundle、批量文件改动、脚本与文档编辑、测试执行、证据采集、哈希与结果复算——**必须优先委派给子模型**，并**尽可能扩大其承担范围**；不得以"自己动手更快""只有我会做"为由把执行工作留在主控。

主控模型只负责：**总体规划、任务拆分、约束与授权边界、关键决策、结果交叉核验、最终验收**。

1. **主控不得把未核验的子模型结论当事实。** 子模型的任何回报都必须经主控核验（读实物、看原始命令输出、比对行号 / diff / SHA256）后，才可写入结论、更新日志、测试报告、交接文档或对外声明。
2. **主控不得以委派为由逃避责任。** 项目铁律、功能冻结、备份纪律、两类独立证据、发版闸门与逐文件 SHA256 全 MATCH、发版后三验、安全与凭据零残留——**一条都不因"是子模型做的"而豁免**；主控永远是最终责任人。
3. **授权与验收权不下放。** 涉及凭据、破坏性动作、功能冻结范围代码与存档格式、交付区与发版的动作，必须由主控先取得**用户当轮明确授权**，并由主控验收；子模型不得自行决定、不得代行、不得先做后报。
4. **委派必须写明边界。** 每次委派须交代：允许改动的路径、明令禁止的动作、需要的证据格式与回报要求；子模型超出该边界的产出**一律不予采信**，并按第 1 条重新取证。
