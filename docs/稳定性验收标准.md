# PCMig 稳定性验收标准（v0.2.29 起生效）

> 一句话目标：**不管中途发生什么，PCMig 最终都不会把任务状态搞乱、不会把数据搞丢，而且能够继续完成。**
> 判定纪律（比"跑通一次"重要得多）：
> **同一个故障连续复现 3 次；修复后连续回归 3 次；并且正常迁移不因此退化。**

## 零、数据安全语义（先把事实定下来，测试才有判据）

| 事实 | 依据 |
| --- | --- |
| 大文件走 robocopy `/Z`（可续传）+ 单线程；小文件走 `/MT` 多线程 | `RobocopyRunner` 双通道设计，`/Z` 与 `/MT` 刻意不同 pass |
| `/COPY:DAT /DCOPY:T /XJ`：拷数据+属性+时间戳，**不跟随 junction/符号链接** | 同上；`/XJ` 排除重解析点 |
| **只有"完全完成"的对象才跳过**；`Failed / CompletedWithErrors / Interrupted` 在续传时一律重跑 | `TransferOrchestrator` 第 190 行注释与实现 |
| 取消/立即停止导致对象中断时，该对象写 `Interrupted` 回执；`Receipt` 是唯一权威 | `MarkInterrupted`、`Receipt` 模型 |
| 传输中的目标文件必然是"半截"的（robocopy 就地写，没有临时文件+改名） | 因此**中断后必须重拷**，绝不能把半截文件当成完成 |

推论（要盯住的唯一风险窗口）：**中断瞬间，目标盘上那个文件是不完整的**。
PCMig 不会把它登记为完成、续传时会重拷（可续传的大文件走 `/Z` 从内部继续），
但"半截文件"在被重拷完成之前，人眼看起来就是一个坏文件——**所以不要在恢复完成前手工使用目标盘的数据。**

## 一、故障注入矩阵（验收表）

| # | 故障 | 注入时间 | 预期状态 | 可恢复 | 数据要求 |
| --- | --- | --- | --- | --- | --- |
| 1 | 正常完成 | — | Completed | — | 100% 一致 |
| 2 | 用户暂停 | 10/30/50/70/90/99% | Paused（确定态） | 是 | 不丢 |
| 3 | 断网 | 20/50% | Interrupted | 是 | 不丢 |
| 4 | 断电/强制关机 | 10/50/90/99% | Interrupted | 是 | 不丢 |
| 5 | Kill PCMig | 50% | Interrupted | 是 | 不丢，无孤儿 robocopy |
| 6 | Kill robocopy | 50% | 对象级重试→继续 | 是 | 不丢 |
| 7 | 目标磁盘空间不足 | 70% | 可恢复失败 | 是 | 已完成部分不回退；释放空间后可续 |
| 8 | 权限拒绝 | 任意 | 对象级失败，其余继续 | 是 | 记录明确 |
| 9 | 文件被占用 | 任意 | FileLocked 分类 | 是 | 解锁后可补齐 |
| 10 | 源文件被删除 | 任意 | SourceMissing 警告 | 是 | 记录，不整体失败 |
| 11 | 源文件传输中被修改 | 任意 | 能识别不一致 | 是 | 报告指出（Final Sync 才能彻底解决） |
| 12 | SMB 会话失效/源机重启 | 任意 | Interrupted | 是 | 不丢 |
| 13 | Job Lock 冲突 | 开始前 | Blocked | 是 | 不并发执行 |
| 14 | Job State 损坏 | 任意 | 可恢复 | 是 | 由 Receipt 重建 |
| 15 | Reparse Point | 扫描 | 排除（Skip + 报告） | — | 不越界 |
| 16 | 组合故障：断网+暂停+关机+恢复 | 任意 | 最终能完成 | 是 | 不丢、状态不乱 |

### 状态机必须"确定"，不允许"界面说暂停、后台还在传"

```
Collecting → PauseRequested → 当前任务安全结束 → Paused → Resume → Running
```

连续点击（暂停→暂停、暂停→恢复→暂停→恢复）不得死锁、不得重复启动 robocopy。

## 二、测试数据盘（不碰真实工作资料）

```
<发版工作副本>-Test\
├── SmallFiles\  LargeFiles\  ManyFiles\  Unicode\  LongPath\
├── LockedFiles\ ReadOnly\   DeepDirectory\ SpecialNames\ ReparsePoints\
```

规模三档：轻量 5–10 GB / 中量 50–100 GB / 压力 300 GB+。
类型不少于：jpg png mp4 zip 7z iso docx xlsx pdf pst db。
超大文件各备：1 GB、10 GB、50 GB、100 GB（大文件与海量小文件是两种完全不同的压力）。

## 三、基线（任何异常测试之前）

同一份数据连跑 3 次正常迁移，记录：文件数 / 字节数 / 耗时 / 平均速度 / 失败数 / 重试数 / 最终状态 / 验证结果。
三次应大致稳定；波动大（如 150→40→180 MB/s）先查清原因再往下做。后续所有异常都与基线对比。

## 四、长时间运行（4–8 小时，无人干预）

观察 RAM / CPU / 句柄数 / 线程数 / 日志增长 / UI 响应 / Job State / robocopy 进程数。
内存健康曲线应是平台期（180→185→182→188），出现 180→250→380→700 就是泄漏，必须定位。

## 五、超大量小文件

10 万 / 50 万 / 100 万文件（总量可能只有 20 GB）分别测：扫描速度、计划生成、迁移速度、
进度准确性（**重点：进度会不会卡在 99%**）、日志体积、内存。

## 六、数据一致性（终极判据，不看"成功"二字）

源 → 文件清单 → 文件数 → 总字节 → Hash（抽样/全量）→ 目标，逐项对齐：

```
文件数：1,283,921 → 1,283,921
字节数：1,842,xxx,xxx → 1,842,xxx,xxx
SHA256：抽样 12,839 / 通过 12,839 / 失败 0
```

## 七、本轮（第一战役）的十项

```
Test 01 正常 100 GB          Test 06 50GB 大文件 + 中途断网
Test 02 100 GB + 50% 暂停     Test 07 空间不足 → 释放 → Resume
Test 03 100 GB + 50% 断网     Test 08 文件锁定 → Resume
Test 04 100 GB + 50% 强制关机  Test 09 100,000 小文件
Test 05 100 GB + 50% Kill PCMig  Test 10 断网 + 暂停 + 重启 + Resume（最重要）
```

Test 10 通过（运行→断网→暂停→关机→开机→恢复网络→Resume→继续→Verify→Hash 一致），
即可认为核心任务引擎进入可接受的稳定阶段；之后再上"连续断网 / 多次暂停 / SMB 服务器重启 /
目标空间变化 / 超大量文件 / 超长路径 / Reparse Point"。
