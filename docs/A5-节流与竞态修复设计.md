#### 口径修正（重要，落地前请采纳）

**修正 1：每行输出实际是 3 个工作项/文件，不是 2 个。**
Core 侧对**每个被复制的文件**至少触发两个事件：
- `FileCopied?.Invoke(full, size)`（`src\PCMig.Core\Transfer\RobocopyRunner.cs:415`）
- `OutputLine?.Invoke(trimmed)`（同文件 `:420`，**对该行无条件触发**）

而 bulk 通道是 `/MT` 多线程模式（`RobocopyRunner.cs:197` / `:210`，`/MT` 下 robocopy **每复制一个文件就打一行**）。所以 2.1M 文件时：
- `OnOutputLine` 的 `Post` → 1 项
- 它能回调里 `Log` 的 `Post` → 1 项
- `OnFileCopied` 的 `Post` → 1 项

⇒ **≥ 3 个工作项/文件 ≈ 630 万工作项**（未计目录头行与 stderr 行；stderr 每行还额外产生 2 项）。主控说的"百万级"成立，实际量级更大。

**修正 2：真正的洪峰不是进度快照，而是日志行 + 文件行。**
Core 的进度上报是**轮询制**：`PollProgressAsync` 每 `Task.Delay(2000)` 才 `Report` 一次（`src\PCMig.Core\Transfer\TransferOrchestrator.cs:638` + `:723` → `:820`），即约 **0.5Hz/对象**。也就是说 `Progress<ProgressSnapshot>` 这条路径本身远低于 10–20Hz 目标；节流的收益几乎全部来自 `OnOutputLine` / `OnFileCopied` / `OnTransferNotice`。

**修正 3：`Progress<T>` 是"异步投递"，换掉它必须自带异常防护。**
`Progress<T>` 把回调 Post 到构造时捕获的同步上下文（WinUI 上是 DispatcherQueueSynchronizationContext）⇒ 每次 `Report` 仍产生 1 个工作项；但它的好处是**永不把异常抛回调用方**。而 Core 调用处 `progress?.Report(new ProgressSnapshot(…))`（`TransferOrchestrator.cs:820`）**没有 try/catch 包裹**。因此：若为了省掉这次投递而换成同步的 `IProgress<T>` 实现，该实现的 `Report` **必须自带 try/catch（绝不外抛）**，否则缓冲区的任何异常会直接杀死传输泵。（对比：Core 对 `OutputLine` / `FileCopied` 自己有 try/catch —— `RobocopyRunner.cs:415-420`、`TransferOrchestrator.cs:200`。）

**修正 4：`Log()` 的截断开销在 UI 线程上是 O(200)/行。**
`while (LogLines.Count > LogLineCapacity) LogLines.RemoveAt(0);` 每追加一行就做一次 200 元素的位移，且每行触发一次 `CollectionChanged` → Step4 的 `LiveLogList` 跟随一次（`Step4ResultPage.xaml.cs:83` 直接把 `session.LogLines` 挂成 `ItemsSource`）。批量刷新天然把这个成本降低 1–2 个数量级。

## 2. P1-5 修复设计（UI 节流 / coalescing）

### 2.1 机制选型

三种候选与判决：

| 候选 | 说明 | 判决 |
|---|---|---|
| ① `DispatcherQueueTimer` 固定节拍（50ms，`IsRepeating = true`） | 项目已有 4 处成熟用法：`MotionState.cs:74-87`（`queue.CreateTimer()` + `Interval` + `Tick` + `Stop`）、`MotionDirector.cs:654-661`、`InteractionFeedback.cs:325-328`、`FluidZoomTransitionCoordinator.cs:724` | **✅ 推荐（作为节拍源）** |
| ② `Stopwatch` 判定 + 按需 `TryEnqueue` | 事件到达时判"距上次刷新是否 ≥50ms"，是才排一次刷新 | **❌ 不作为唯一机制**：只有前边沿、**没有后边沿**。最后一次事件之后若不再有事件（例如复制完最后一个文件后进入 45 秒停滞），那批数据**永远不会上屏** —— "最近一个文件"会一直停在旧值，属于正确性缺陷，不是性能取舍 |
| ③ 只用一个"已排队"合并标志 + `TryEnqueue` | 队列里最多 1 个刷新工作项，谁进来谁把缓冲排空 | **❌ 不作为唯一机制**：它把**队列深度**压到 1，但**不限制速率**——UI 线程会被这个自我重排的刷新项连续占满（每当它跑完，若又有新数据就再排一次），洪峰时仍然饿死输入与绘制，"界面卡住"的用户观感不变 |

**推荐组合：① 做节拍源 + ③ 只用于"跨线程启停 timer / 立即项投递"。**
理由：
1. 唯一能同时给出**频率上界（20Hz）**与**尾边保证**的是固定节拍 timer；
2. 本项目对 `DispatcherQueueTimer` 的两个已知坑都有**成文结论与既定做法**，不是新机制：
   - **必须持强引用**，否则被 GC 回收 ⇒ 回调永不触发（`MotionDirector.cs:645-648`、`InteractionFeedback.cs:328`、`PageTransitionCoordinator.cs:22`）；
   - **必须在进程退出前 Stop**，否则命中 WinAppSDK 卸载期缺陷（`MotionState.cs:103-108`）。
   本设计要求与这两条对齐（§2.5），并在 §6 加静态契约测试防止"忘接线"。
3. **明确禁止**的替代做法：`Task.Run(async () => { while (true) { await Task.Delay(50); … } })` 之类的自转循环——它没有与 UI 线程绑定的停止路径，任务结束后会变成幽灵刷新源，正是"再叠一层不可靠机制"。

WinUI / WinAppSDK 版本核对：`PCMig.WinUI.csproj` 是 `net8.0-windows10.0.19041.0` + `Microsoft.WindowsAppSDK 2.5.1` + `WindowsAppSDKSelfContained` ⇒ `DispatcherQueueTimer`（`Microsoft.UI.Dispatching`）可用，与既有 4 处用法同源。

**间隔定案：50ms（20Hz）。** 依据：Core 的进度快照本身只有 ~0.5Hz，50ms 对数值位毫无可感延迟；对日志/文件流给到人眼舒适的上限；20Hz × 200 条窗口是 ListView 可承受的量级。

### 2.2 缓冲结构与线程安全

生产者在**引擎线程/线程池线程**上（`RobocopyRunner` 的 stdout 泵与 stderr 泵是两个并发任务 ⇒ 真·多生产者；`TransferOrchestrator` 的进度轮询是另一个）。消费者在 **UI 线程**。

**结构（推荐）**
- 一把 `private readonly object _gate = new();`
- `Queue<string> _pendingFiles`（容量 200）
- `Queue<UiLogEntry> _pendingLogs`（容量 200）
- 标量：`string? _latestFileText`（"最近一个"，**不参与容量丢弃**）、`TSnapshot? _latestSnapshot`（最新值胜出）
- 计数：`int _droppedFiles` / `int _droppedLogs`（累计，运行开始时清零）

**为什么用 `Queue` 而不是 `List`**：入队溢出时要丢最旧一条。`List.RemoveAt(0)` 是 O(n) 位移，按 630 万次入队 × 200 元素 ≈ 12 亿次搬移，不能接受；`Queue.Dequeue()` 是 O(1)。

**为什么用锁而不是 `ConcurrentQueue`**：临界区只是"入队 + 计数 + 溢出出队"，无阻塞 IO、无嵌套锁；用 `ConcurrentQueue` 反而要处理"无锁情况下如何原子地判容量与丢最旧"（需要额外计数与竞态处理）。锁的实现更短、更容易证明正确。若日后测出锁竞争（20 个 robocopy 线程同时打日志），再换 `ConcurrentQueue` + 单消费者计数也不迟。

**Drain 的关键细节：绝不持锁应用批次。**
```
Drain():                       // 只在 UI 线程调用
  lock (_gate):
    var files = _pendingFiles; _pendingFiles = new Queue<string>(cap);
    var logs  = _pendingLogs;  _pendingLogs  = new Queue<UiLogEntry>(cap);
    var latest = _latestFileText; _latestFileText = null;
    var snap = _latestSnapshot;   _latestSnapshot = null;
    var dropped = (_droppedFiles, _droppedLogs);
  // 出锁之后再 ToArray / 应用到 ObservableCollection
```
即：锁内只做 O(1) 的引用交换，生产者最多被阻塞几十纳秒。

**`Report` 的替换（对应修正 3）**：把 `new Progress<ProgressSnapshot>(s => Post(() => ApplySnapshot(s)))`（快照 `:1184`）换成 VM 内部一个 `sealed class SnapshotSink : IProgress<ProgressSnapshot>`：
```csharp
private sealed class SnapshotSink : IProgress<ProgressSnapshot>
{
    private readonly Action<ProgressSnapshot> _onReport;
    public void Report(ProgressSnapshot value)
    {
        try { _onReport(value); }     // 必须自带 try/catch：Core 调用点无保护
        catch { /* 绝不外抛：否则杀死传输泵 */ }
    }
}
```
两点收益：省掉每快照 1 个工作项；并且快照可以在引擎线程直接落到"最新值"槽位。

### 2.3 批量刷新的粒度（这里是安全边界）

**按 10–20Hz 节拍刷新的量（只有三类高频流）**
| 量 | 说明 |
|---|---|
| `CurrentFileText` | 显示"最近一个"，取 `_latestFileText`（即使它的行已被 200 容量丢掉，也必须保留） |
| `LiveFiles` | 批量追加 + 维持 200 上限 |
| `LogLines` | 批量追加 + 维持 200 上限（含引擎行与错误行的追加） |
| `ApplySnapshot` 的**数值位** | `Percent` / `ProgressText` / `PlanBytesText` / `ActualBytesText` / `BalanceText` / `ObjectText` / `EngineSpeedText` / `EtaText` / `DataLabel` / `FailedObjects` / `CurrentObjectPath` / `CurrentObjectDetail` / `StallSeconds` / `StallHintText` / `ApplyObjectRowStatus` 的行状态 —— 最新值胜出 |

**绝对不可被节流延迟的量（必须立即上屏）**
1. **用户即时操作的反馈**：`PauseAsync` / `StopAsync` / `ResumeAsync` 路径上的 `StatusMessage`、`IsPaused`、`Phase`，以及底栏按钮态 `CanPause` / `CanStop` / `CanResume` / `CanStart`（由 `RaiseDerived()` 广播，`MainWindow.PushFooter()` `:346-368` 与 `Step3ProgressPage.PushState()` 消费）。延迟 50ms 会变成"点了没反应"。
2. **阶段切换**：`ApplySnapshot` 里若 `s.Phase != Phase` ⇒ **立即整体应用**（不走缓冲）。理由不只是 50ms 延迟，更是**防错序**：同一节拍窗口内若先到 `Paused` 再到 `Running`，"最新值胜出"会把暂停态整段跳过，界面上就看不出曾经暂停过。
3. **结束/失败/中断**：`FinishRunAsync` 的 `Percent`（`Completed ⇒ 100`）、`DataLabel`、`BalanceText`、`StatusMessage`、`IsFinished`（快照 `:1228-1274`）必须立即；**并且在应用之前先 `FlushPendingNow()`**，否则最后一批引擎日志与"阶段结束"这类动作行会顺序颠倒，或者那批日志永远不上屏。
4. **失败/不一致条目的产生**（`AddFail` 的立即路径，如 `OnTransferNotice` 的速度异常、`RefreshRowsFromReceiptsAsync` 的对象失败行、`ApplyVerifyToRows` 的校验不一致）——单发事件必须立刻可见。
   边界说明：**引擎逐行输出里被判定为错误的行**（`OnOutputLine` 的 `isError` 分支）允许随批量在 ≤50ms 内出现；理由是那可一次出现上千条，"每条立即"等于把洪峰搬回 UI 线程。这条差异必须在代码注释里写清，否则后人会以为漏了。
5. **预检/扫描/验证的动作行**（`Log(...)` 的既有调用点，天然低频）。
6. **任务切换/复位类**：`ResetForJobSwitch`、`ResetRunProjection`、`HasPlanReset` 等（切任务后界面必须马上正确，不能残留上一个任务的行）。

**实现取舍（最小改动面）**：保留既有 `Post(Action)` 与 `Log(level, text)` 的语义，新增一个"立即通道"：
```
PostImmediate(Action apply):        // 立即项唯一入口
  Post(() => { FlushPendingNow(); apply(); })    // 先排空缓冲 ⇒ 保证日志/集合的先后顺序
```
只有 **3 个生产者**切到批量通道：`OnOutputLine`（引擎行 → `EnqueueLog`）、`OnFileCopied`（→ `EnqueueFile`）、进度快照（→ `SetLatestSnapshot`）。其余约 30 处 `Log(...)` 调用点**一行都不用改**（自动获得"先排空、再立即"的语义）。

### 2.4 容量与丢弃策略（诚实表达，不得假装完整）

- **入库即限容**（关键）：容量判定必须在**生产者侧入队时**做，不能等刷新时再做。否则 UI 线程被卡 3 秒就会在内存里堆下十万条字符串 —— 那比工作项风暴更危险。
  - `EnqueueFile`：`if (_pendingFiles.Count >= fileCapacity) { _pendingFiles.Dequeue(); _droppedFiles++; }` 再入队；
  - `EnqueueLog`：同上（`_droppedLogs++`）；
  - `_latestFileText = text` **无条件覆盖**（"最近一个"不能被容量丢掉）。
- **刷新时维持 UI 集合的 200 上限**：沿用既有 `while (Count > capacity) RemoveAt(0)`；因为批量最多 200 条、集合上限也是 200，最坏情况下也是一次 200 条位移，20Hz ⇒ 4000 元素位移/秒（相对今天每行一次，降了 3 个数量级）。
- **大批量时的批量追加优化（可选）**：当本次批次的条数 ≥ 阈值（建议 32）时，改成"整窗替换"（`Clear()` + 重新填 200 条）⇒ 2 次 `CollectionChanged` 而不是最多 400 次。代价是滚动位置重置；已核实两个面板**都没有**自动滚动到底的逻辑（全仓 grep `ScrollIntoView` / `ChangeView` 只命中 `MainWindow.xaml.cs:737` 的一句注释），所以不存在"跟随尾部"被破坏的回归。此项为优化，不是必须。
- **被丢弃的条数必须在 UI 上如实表达**（用户明确要求「不得假装成完整」）：
  - 新增两个只读属性（示例名）：`LiveFilesOmittedText`、`LogLinesOmittedText`，文案口径建议：
    - `LogLinesOmittedText`：`"…本次运行另有 N 行较早输出未在本面板显示（面板只保留最近 200 行；完整日志见任务目录 <路径>）"`
    - `LiveFilesOmittedText`：`"…本次运行另有 N 个较早文件未在本列表显示（列表只保留最近 200 个）"`
  - 计数是**运行内累计**（不是"本次刷新丢弃数"），`Clear()` 时归零；
  - 呈现方式两选（**需主控确认，因为触及 XAML/绑定**）：
    - **方案 P（推荐，零 XAML 改动）**：把这条提示当作**真实的一行**插进 `LogLines`/`LiveFiles` 本身（复用既有 `SessionLogLine`，level 用 `WARN`）。优点：不需要改任何 XAML/绑定；缺点：它会占用 200 容量里的 1 个位置，且更新时要做一次"替换首/尾行"。
    - **方案 Q（最小 XAML 改动）**：Step3 与 Step4 各加一个 `TextBlock` 绑新属性。优点：语义干净（提示与数据分离）；缺点：**改 XAML 与绑定**，按死律 #1（功能冻结：禁止动绑定）属于需用户当轮明确授权的动作。
  - **明确禁止的写法**：把提示写成静态文案（例如恒定显示"…还有 N 行"）——那就是假装；N 必须来自真实计数。
- **D1（失败清单）建议一并处理**：给 `FailItems` 加同样的容量（建议复用 `LogLineCapacity = 200`）+ 累计丢弃计数 + 诚实提示（"另有 N 条失败未在此列出，完整清单见报告/日志"），并给 `_failIndex` 加增长闸门（达到容量上限后只计数不再新增键）。**此项待主控确认是否纳入本轮。**

| 时点 | 动作 | 依据/落点 |

## 3. P2-6 修复设计（Host 输入的异步探测竞态）

### 3.1 选型：debounce **与** generation token **两者都要**（推荐）

| 机制 | 单独用够不够 | 理由 |
|---|---|---|
| 只用 debounce | 不够 | debounce 合并的是**请求的发起**，管不住**在途请求的返回**：用户在 400ms 内敲 3 个字符 ⇒ 触发 1 次探测，但在这次探测返回前用户又敲了 2 个字符 ⇒ 第二次探测启动，第一次的结果稍后返回并**覆盖**新状态 |
| 只用 generation token | 够安全但浪费 | 它只保证"旧结果不覆盖新状态"，**不阻止**每个字符都发起一次全量 `ListAll()`（§1.2 B5 的 IO 量级）—— 输入 20 个字符就是 20 次全量任务目录扫描 |
| 只做"连接成功后再探测" | 不够且会退化 | 它会丢掉两个既有语义：① 启动时的"尚未连接 ⇒ 无法匹配（≠ 没有未完成任务）"如实回报（`FindUnfinishedOnStartupAsync` 快照 `:1574-1580` 与注释 `:1544-1546`）；② 同一 host 重连后需要再探测一次 |

**推荐组合（三件套）**：
1. **连接门**：由 `Host` 变化触发的探测，在 `IsSourceConnected == false` 时**不做任何 IO**；
2. **debounce 400ms**（建议区间 300–600ms）：`Host` 连续变化只在最后一次之后 400ms 才真正发起；`IsSourceConnected` 的 **false→true 跳变立即发起**（这是用户按下"连接"之后的真实时刻，不该被去抖延迟）；
3. **generation token + key 快照**：详见 3.3。

### 3.2 归属：把去抖与门控放进 Session，而不是 Shell

推荐新增（`MigrationSessionViewModel`）：
```csharp
/// Host / 连接状态变化后的“未完成任务探测”请求（去抖 + 连接门 + 世代作废）。
/// 非阻塞、无返回值、绝不外抛异常 ⇒ Shell 侧不再需要 async void。
public void RequestUnfinishedProbe();

/// 关闭/退出时停止去抖计时器（与 UI 节流的停止同一处生命周期纪律）。
public void StopUnfinishedProbeTimer();

/// ★ 测试缝（仅单测可赋值；生产恒为 null ⇒ 走 Core 的 JobManager）★
public Func<string, string?, IReadOnlyList<JobSummary>>? UnfinishedProbeForTest { get; set; }
```
理由：
- `MainWindow.xaml.cs:280` 现在是 `async void`（无法被 await、无法观测异常、可并发重入）。把入口改成**同步的 `RequestUnfinishedProbe()`** 后，Shell 侧变成普通事件处理，**彻底消除 async void**；
- 去抖与世代判定都必须作用在"写 `UnfinishedProbeText` / `PendingResumeCandidate`"的地方，而写操作发生在 Session 内部 ⇒ 门控必须在 Session 里，否则 Shell 只能挡住"发起"，挡不住"旧结果回来"；
- `UnfinishedProbeForTest` 与既有 `TransferRunner` 测试缝（快照 `:611-633`，注释明确写着"装配层绝不可设置本属性"）**同一纪律**，可直接照抄那段注释与 `_log.Warning`。

### 3.3 "旧结果不得覆盖新状态"的具体判定

请求按此顺序执行：
1. `var key = Host;                    // 本请求的 host 快照`
2. `var token = ++_probeGeneration;    // 单调递增（Interlocked.Increment）`
3. `_probeCts?.Cancel(); _probeCts = new CancellationTokenSource();`（把上一个在途请求的 `Task.Run` 取消；`JobManager` 内部不可中断，但 `Task.Run(..., ct)` 至少不会启动新工作）
4. `await Task.Run(() => probe(Host, target), ct)`
5. 返回后，**先判门再写状态**：
   ```csharp
   if (token != Volatile.Read(ref _probeGeneration)) return;   // 有更新的请求存在 ⇒ 整个结果作废
   if (!string.Equals(key, Host, StringComparison.Ordinal)) return; // host 已变 ⇒ 结果已过期
   ```
6. 只有通过第 5 步才写 `UnfinishedProbeText`、`PendingResumeCandidate`、以及 `Log(...)`。
7. 异常路径同样先过第 5 步的判门（否则旧请求的报错会覆盖新状态）；异常本身照旧如实写 `"未完成任务检测失败：{ex.Message}"` + `Log("ERROR", …)`。

**为什么两者都要**：token 挡住"并发重入"（同一 host 上两次请求先后返回），key 快照挡住"host 已变但世代没变"的边角（例如去抖计时器在同一 host 上重复触发、或外部直接调用 `FindUnfinishedOnStartupAsync`）。两个判定都通过才写，代价是两次比较。

### 3.4 两个触发源的差别处理

| 源 | 触发时机 | 处理 |
|---|---|---|
| `Host` | 逐字符（`UpdateSourceTrigger=PropertyChanged`） | debounce 400ms → 到期后判连接门：`IsSourceConnected == false` ⇒ **不 IO**，只把 `UnfinishedProbeText` 写成"尚未连接 ⇒ 无法匹配（≠ 没有未完成任务）"的既有文案（**若文案未变则不写**，避免无意义的 PropertyChanged 风暴）；`IsSourceConnected == true` ⇒ 发起探测（key = 到期那一刻的 `Host`） |
| `IsSourceConnected` | 连接成功/断开（低频、语义明确） | **false→true 立即探测**（不去抖）；**true→false** 只重置提示与 `PendingResumeCandidate`（可选，需主控确认是否清空候选），不发起 IO |

**去抖的实现要求**：用 `DispatcherQueueTimer`（`IsRepeating = false`，`Interval = 400ms`），遵守 §2.5 的同两条纪律（强引用 + 关闭前 Stop）；禁止 `Task.Delay` 后 fire-and-forget（没有停止路径、也没有"谁负责写 UI 状态"的明确归属）。**不建议**引入第二个 timer 的另一种理由：与 §2.5 的关闭路径共用同一个 `StopUiRefresh()` 出口，把"忘接线"的风险收敛到一处。

### 3.5 相邻修正（B 的配套，建议同批落地）

1. **`PendingResumeCandidate` 变化要发通知**：现状是无 `Raise` 的自动属性（快照 `:591`），所以 Shell 才手工调 `PageResult.RefreshFromSession()`（`MainWindow.xaml.cs:271`）。建议在探测里当引用变化时 `Raise(nameof(PendingResumeCandidate))`，让 Step4 的 `PushState()`（订阅 `OnSessionChanged`，`Step4ResultPage.xaml.cs:119`；消费点 `:139-140`、`:152`）自行刷新，**不再依赖 Shell 的一次性手工调用**（否则任何新增调用方都会静默不刷新）。
2. **Shell 侧订阅保持一处**：`MainWindow.xaml.cs:192` 的订阅可保留在同一个位置，但处理体改成同步的 `Session.RequestUnfinishedProbe();`；启动的 `probeRoot.Loaded → ProbeUnfinishedAsync()`（`:193-196`）保留（那是一次性的显式探测，语义与文档一致）。`Session.PropertyChanged` 无需退订（窗口与进程同生命周期，关闭走 `Environment.Exit(0)`）。
3. **载体收口**：`FindUnfinishedForPrepareAsync`（快照 `:1607`）是预检链的显式调用（有 host/targetRoot 入参、有调用方等待返回值），**不走** debounce，但建议它也接受同一个世代门（或在文档里明确它不受输入风暴影响——因为它只在用户点"生成计划"时调用一次）。**这一点我倾向后者：不要为了统一而给它加不必要的东西。**

## 4. 问题 C 修复设计

### 4.1 C1：`ChildrenLoaded` 改为"成功后才置 true"

**改法（最小且不破坏既有 UI 判定）**
1. 在 `EnsureChildrenAsync` 里**删掉** await 之前的 `node.ChildrenLoaded = true;`（快照 `:192`）；
2. 新增一个**私有重入守卫**：`private readonly HashSet<DirNode> _loading = new();`（或 `DirNode` 上加 `internal bool ChildrenLoading { get; set; }`）—— 首行改成：
   ```
   if (node.ChildrenLoaded || _loading.Contains(node) || string.IsNullOrEmpty(node.FullPath)) return;
   _loading.Add(node);
   ```
   并在 `finally` 里移除（与 `IsLoading = false` 同一处）；
3. **在成功路径的 UI 线程块内**（即 `await OnUiAsync(() => { node.Children.Clear(); … })` 这一步）最后一行置 `node.ChildrenLoaded = true;` —— 与 UI 集合的变更在**同一次 UI 线程执行**内完成，避免"集合已换、标记还没换"的中间态被 `BuildNode`/`SyncNodeChildren` 观察到；
4. **失败与版本失效两条路径都不置 true** ⇒ 下次展开自然重试；
5. 可选但推荐（**诚实性**）：失败时用既有 `Notice` 事件（`DirectoryTreeViewModel.cs:58`，已有两处用法 `:269`/`:276`）报一句真话，例如
   `Notice?.Invoke($"目录「{node.Name}」读取失败（{ex.Message}）——再次点击展开可重试。")`；
   用量：只报"首次失败 + 同节点最多一次"（加一个 `_noticeShown` 标记或复用 `_bigDirHintShown` 同款做法），避免反复展开时刷屏。

**为什么保留 `bool ChildrenLoaded` 而不是立刻换三态枚举**
`ChildrenLoaded` 已被 UI 侧当作"是否补占位箭头"的唯一判据：`Step2SelectDataPage.BuildNode`（`:183`）、`SyncNodeChildren`（`:213`）、`DirTreeModels.AddDummy`（`:76`）、`RecomputeFromChildren`（`:126`）。换成枚举就要同时改这 4 处 + QA 探针里那句 `m.ChildrenLoaded = false;`（`:69`）。**建议先做最小修正**（行为已正确）；若后续需要"正在展开…"的逐节点指示，再引入
```csharp
public enum NodeLoadState { NotLoaded, Loading, Loaded }
public NodeLoadState LoadState { get; set; }
public bool ChildrenLoaded => LoadState == NodeLoadState.Loaded;   // 只读兼容投影
```
—— 注意那会**破坏** QA 探针里的赋值语句（`:69`），必须同批改掉（该探针是取证工具，非产品语义）。

**失败后用户如何重试（回答主控的问题）**：用户只需要**再点一次展开箭头**。可达性已核实：`DirTreeView_Expanding`（`Step2SelectDataPage.xaml.cs:424-431`）每次展开都会调 `EnsureChildrenAsync(model)`，随后无条件 `SyncNodeChildren(node)`；由于失败时 `ChildrenLoaded` 仍为 false，`SyncNodeChildren` 会在末尾补一个空 `TreeViewNode` 占位（`:213`）⇒ 箭头仍在 ⇒ 用户可再次点击 ⇒ 真正重读盘。**不需要**新增"重试按钮"或右键菜单。

**顺带记录的一个既有小瑕疵（不建议本轮改）**：`IsLoading`（`:54-55`）是 VM 级单一布尔，多个节点并发加载时会互相提前复位；`finally { IsLoading = false; }`（`:292`）在多节点并行时不准。它只影响"正在展开…"提示的准确性，与本次缺陷无关，仅登记。

### 4.2 C2：`InvalidateInFlightBrowses()` 的调用点

**它该在哪些时机被调用（按必要性排序）**

| # | 时机 | 落点（具体到方法） | 理由 |
|---|---|---|---|
| 1 | **连接重新建立 / 主机切换** | `Step2SelectDataPage` 的 `AttachConnection` 路径（`:684-700` 一带：`_shellConnection.Shares` 的订阅建立处）与 `OnShareItemChanged`（`:704-708`）之后、`SyncTreeRootsFromShares()` 之前/之后各一次 | 这是它与 `_browseVersion` 语义的原始设计意图（注释原文：「连接已重新建立：作废在途的懒加载结果」，`:158`）。换主机后旧的 UNC 枚举结果**必须**作废，否则会把上一台机器的目录树画到新主机上 |
| 2 | **共享列表被重建**（`SyncRoots(IEnumerable<ShareRootSpec>)` 内部，只要发生了"根被移除"或"新增了根"） | `DirectoryTreeViewModel.SyncRoots`（`:103-156`，删除分支 `:114-121`） | 根集合变了 ⇒ 在途结果对应的节点可能已不在树上（其 `Parent` 链断裂），继续回填会往孤儿节点写数据 |
| 3 | **Shell 层察觉到主机变化时**（`MainWindow` 的 `UpdateSourceStatus` 路径，`MainWindow.xaml.cs:173-178`） | 由 Session 转发给 Tree（例如新增 `Session.InvalidateTreeBrowses()` → `Tree.InvalidateInFlightBrowses()`） | 兜底：任何绕过 Step2 页面订阅的连接变化路径都能作废 |
| 4 | **关闭/退出** | 不需要 | 进程即将退出，且 `Environment.Exit(0)` 会直接结束 |

**明确"不需要"的两处（纠正可能被想当然加入的调用点）**
- **切页（`StepNavigation.GoTo`）不需要**：目录树是 Step2 页的视图，切走再切回不改变任何 UNC 读取的有效性；在这里作废只会让用户白等一次读盘。
- **"页面销毁"不需要**：本应用没有页面销毁（见 §2.5 表格最后一行）。

**与 `_browseVersion` 的配合**
- `EnsureChildrenAsync` 启动时 `var v = version ?? _browseVersion;`（快照 `:193`），返回后 `if (v != _browseVersion) return;`（`:242`）—— 语义即"代次不匹配就丢弃结果"；
- C1 修好之后，这条丢弃路径**不再留下永久失效的节点**（`ChildrenLoaded` 仍为 false，箭头仍在，用户再点一次就重新读）—— **两条修复是互补的：C2 提供作废能力，C1 保证作废后仍可恢复**。所以 C1 与 C2 建议**同批落地**，只做 C2 会让"作废后节点永久不可展开"的概率从 0 变成常态（一旦真的接线）；
- 线程安全：把 `_browseVersion` 的读/写改为 `Volatile.Read(ref _browseVersion)` / `Interlocked.Increment(ref _browseVersion)`（或明确写死"仅在 UI 线程访问"的注释纪律）。`InvalidateInFlightBrowses` 的调用点全部在 UI 线程（连接事件、页面事件），所以实际上单线程；但 `_queue is null` 的 QA/离屏路径下续体可能不在同一线程。
