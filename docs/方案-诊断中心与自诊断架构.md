## 0. 审查结论与边界

推荐建设**本地优先、无 AI、观察式、有界资源、显式证据完整性**的诊断系统，而不是日志窗口。批准方向不等于批准所有候选细节。

需要推翻/修正的关键假设：

1. Analyzer 不以磁盘成功为先决条件；在线事件分析与持久化并列，历史回放才读磁盘。UI 从不成为生产/规则执行依赖。
2. 没有 UserActionObserved 不能证明用户点击未被接收；没有独立意图证据时结论只能是“无记录/不可判定”。
3. **有界内存 + 永不阻塞业务 + 任意故障下零丢失不可兼得**。承诺可度量损失、优先级保留、明确降级，不承诺无限可靠。
4. Sequence 是进程内唯一排序键，不是跨线程 happens-before，也不保证异步通道的物理写入顺序；因果由显式 parent/cause 证明。
5. `FileCopied` 实际是文件开始/尝试行；ProgressSnapshot 字节含估计、回冲、目标 stat 等口径，不能当逐文件成功审计。
6. 当前没有贯穿 Core/VM/View 的业务 StateVersion。新增的是诊断 ObservationVersion，不写入 JobState，不创造第二状态机。
7. “Paused ⇒ ResumeAvailable”目前与真实 `CanResume` 不符；作为已知交互矛盾单独登记，**不为实现反馈契约而修改暂停/恢复行为**。
8. 当前 Robocopy 已始终 `/TEE /UNILOG+`，Job logger 也以 Debug 逐行持久化。新诊断 Operational 不记 per-file，不代表当前产品已无逐文件日志开销；两者必须区分。
9. Privacy、self-health、队列故障和性能探针必须前置，不能等导出或最后验收再补。
10. 不建设无限 Correlation Graph 或逐文件 Activity。生命周期索引按 operation/action 有界，已结束项归档后淘汰。

本方案所有 instrument 点未来都需独立明确授权；允许新增观察点不等于允许改变 Planner、迁移参数、Receipt、JobPhase、Verify/Repair 行为。

### 1.3 本轮最重要的真实链路

`Click handler → 既有 guard/Session方法 → Core调用 → ProgressSnapshot/三事件/存档 → SnapshotSink/UiBatchBuffer → ApplySnapshot → PropertyChanged → PushFooter/PushState → 命名控件`。

每个箭头目前缺少统一的身份和独立交付结果。中文字符串、UI 接收时间、近似进度不够重建动作链。这是最大的端到端盲区。

## 2. 可复用内容及复用限制

直接复用：JobId/ObjectId、Receipt 权威口径、JobPhase/PhaseView、RobocopyRunResult、Win32/HResult 原始异常、IProgress/OutputLine/FileCopied 已有发布边界、UI batch 的生产者限容/固定节拍/尾批先刷纪律、既有材质与工具面动画。

需要适配：ILogger 当前类型是 **Serilog.ILogger**；ProgressSnapshot 无 Session/Operation/StateVersion；PreflightCheck.Name 是展示文字；MemorySink 丢掉结构；快照中的当前路径属 Personal；现有 ErrorLines 有上限，不能当完整失败清单。

仅作历史证据：旧文本日志、旧 jsonl、poc-startup、QA 环境变量探针；历史解析标注 Legacy/Partial，**不补造它们没有的 EventId/因果**。冻结目录树和 Task Picker 只识别现有调用点，不重新审计实现正确性。

## 3. 关键盲区与风险分级

1. **UI 语义链不闭合**：Click 未到、guard return、方法进入、Domain受理、VM赋值、控件投影目前不可区分。
2. **Persistence 实际结果缺失**：WinUI 未挂 `JsonStateStore.OnWarning`；TryRead=false 无法区分不存在/损坏/权限。WriteAtomic 对所有已存在目标采用同样 skip 分支，并非类型识别“仅视图”。不能在方案中把注释提升成保证。
3. **Verifier evidence completeness**：`Directory.Exists=false` 可得零统计；hash failure 未增加 mismatch；MissingSamples 不参与 Status 表达式；空列表 All 可真。仅登记 Stage B 证据需求，不修语义。
4. **请求态和真实暂停态混用**：PauseAsync 先置 IsPaused；Core cooperative 等对象边界并驻留 WaitIfPausedAsync，VM IsRunning 可仍 true，CanResume=false。这是已交接矛盾，不作为本轮新事故反复测试。
5. **原生日志过量**：Job logger Debug 收 stdout，每行再写文本+JSONL，Robocopy 自己另有 UNILOG；后续性能测量必须包含这些既有成本。
6. **异常尾部与写盘退化不可见**：多个 logger 无集中 dispose；部分事件订阅和 pump catch 丢原因；无明确 clean marker。
7. **具体网络根因不可推定**：文件访问失败不能分辨 VM关机/SMB服务停/防火墙/线路断；显示候选与下一检查，不制造“远端已关机”事实。
8. **观测失败等于证据不足**：日志被丢、UI线程堵塞、页未挂载时禁止确定性缺事件判错。

这些是静态可见风险，不是本轮新故障复现结论；不为逐条证实重跑封板测试。

## 4. 对候选架构的技术批判

- Hub 热路径只做轻量身份、受控字段验证/裁剪、分类、计数、TryWrite；不全图查询、同步序列化、枚举磁盘、调用 UI 或 arbitrary callback。
- Redaction 不能只放在 Persistence：Secret 必须在入口就不存在；Flight Recorder、Activity tags、Emergency、快照也受同一策略。
- Analyzer 与 Writer 使用独立 reader 分支；**两个消费者读同一个 Channel 是竞争消费，不是广播**。显式 fan-out、每条分支各自 loss ledger。
- 无有界重排可保证任意迟到都被严格顺序排序。保留 Sequence，在回放排序；在线规则用因果键/宽限/证据水位，不能等缺失 sequence 永久阻塞。
- 顶层模块不各建 project。用两个小的净依赖项目＋WinUI 目录，见 §28–29。
- 不采用一般 CEP/规则 DSL/动态脚本/图数据库：强类型确定性规则和可控时间源更易测，避免用户数据变成执行代码。
- 不应把轮询所有控件、每文件 span、每 expectation Timer、每日志 Dispatcher callback、自动网络探测当“完整观测”。
- “Root-cause cards”改为“事件卡/候选原因卡”；对证明充分的 Win32失败可给高证据强度，对物理原因通常只给候选。

## 5. 推荐架构

```text
UI handlers / VM / Core / Native boundaries
  → Typed diagnostic publisher (NoOp可用、非抛、Secret不入)
  → bounded ingest [critical reserve | operational | verbose]
       ├→ background normalization / explicit fan-out
       │    ├→ analyzer inbox → contracts/rules → incidents
       │    ├→ writer inbox → JSONL segments + acknowledgement watermark
       │    └→ viewer cache (没有viewer照常运行)
       └→ compact flight ring + bounded disk checkpoints

Meter → bounded aggregate sampler → metrics snapshots
ActivitySource → optional listener/exporter（不负责业务ID）
Health counters / emergency slots → 独立监督，不递归进故障sink
Read-only Snapshot providers → Incident附件（时间/完整性有标注）
Export service → sealed segment lease → redact DTO → zip + hashes
```

为了保留 trigger 前近尾，Flight compact ring 在入口受控地写入固定预算槽；大型/raw载荷先裁剪，不把未脱敏对象放进 ring。Trigger 快速切换 ring 段引用，序列化交后台。

Composition root 在 WinUI App 尽早启动，早于 ConnectionVM/Session logger 使用；CLI/WPF 将来各有适配，不一次全迁。诊断服务不能引用 Core 业务类型来修改状态；Core 只依赖契约。Viewer 与 Export 在它们未打开时不被构造。

## 6. DiagnosticEvent 正式数据契约（v1 草案）

区分**事件类型ID**和**事件实例引用**。事件实例以 `(SessionId, Sequence)` 唯一标识；不要把 `NET-001` 放进 Incident 的 EvidenceEventIds 当成某一次证据。

| 字段 | 类型/要求 | 口径 |
|---|---|---|
| SchemaVersion | string，必填，如 1.0 | envelope协议；与业务存档版本完全独立 |
| Sequence | int64，必填 | 每进程 Interlocked.Increment；JSON写数值，JS消费者按64位安全协议处理 |
| SessionId | 128-bit随机ID，必填 | 每次进程启动新建；显示可缩写，不用4位短ID作唯一键 |
| TimestampUtc | UTC ISO8601，必填 | 发生/发布时，不是UI展示时间 |
| MonotonicTimestamp | int64，必填 | Stopwatch.GetTimestamp；frequency及UTC锚点在session元数据 |
| EventId / EventName | 稳定code / stable name，必填 | 1:1；名称可由catalog省略传输但落盘保留便于离线读 |
| EventVersion | int，必填 | 单种事件payload演进 |
| Level / Category / Component | 枚举/稳定短名，必填 | 不使用用户自定义无限字符串 |
| DeliveryClass | 枚举，必填 | DurableCritical / Operational / Verbose，与严重级别不同 |
| Outcome | 枚举，可选 | Started/Accepted/Rejected/Succeeded/Failed/Canceled/Skipped/Unknown；不是JobPhase |
| JobId / ObjectId | string，可选 | ObjectId必须与JobId联合；不把同名object跨Job合并 |
| ActionId / OperationId | 128-bit ID，可选 | 语义交互/一次运行；各自可独立存在 |
| ParentOperationId | ID，可选 | **补充字段**，Activity为null时仍能建树 |
| RunGeneration / Attempt / Pass | 标量，可选 | 防旧运行/旧投影串入新任务；retry身份明确 |
| TraceId / SpanId / ParentSpanId | W3C字段，可选 | 有Activity才填；没有则null，不伪造匹配关系 |
| CausationId | EventRef，可选 | 直接原因的事件实例；多因关联用有限 Links |
| CorrelationId | 可选 | 跨session请求/测试scenario等额外关联；已有Operation时不重复堆同义ID |
| Phase | 可选 | StateOwner+ObservedPhase，区分Core/VM/View/StoredState |
| StateVersion | 可选 | 仅未来真实业务存在时采用；本阶段用独立 ObservationVersion+StateOwner，不伪造 |
| ObservationVersion / ProjectionVersion | int64，可选 | 诊断来源域内序号，包含RunGeneration；View ack引用确切source event |
| Message | 可选、有长度上限 | 仅presentation；catalog resource+参数优先，不用于规则 |
| Path / PathHash | PathRef结构，可选 | 多源/目标用role区分；默认token化，HMAC带KeyId/Scope；完整路径受策略控制 |
| ExceptionType / HResult / Win32Error / RobocopyExitCode | 可选 | 错误域分离，保留signed/raw；不可盲取HResult低16位当Win32 |
| DurationMs | number，可选 | monotonic计算；不得负数/NaN/Infinity |
| ThreadId / ProcessId | 可选 | PID主要session/child记录；ThreadId只深诊断和线程错误场景 |
| Metadata | 有界、白名单、扁平typed字段 | 禁任意object、委托、Exception.Data、VM/credential对象解构 |
| EvidenceQuality / CaptureMode | 枚举，必填或session继承 | Direct/Derived/Estimated/Legacy；Operational/Flight/Deep |
| Truncated / LossEpoch / ContractVersion | 可选 | 裁剪、分支丢失世代、反馈契约版本 |

省略null、不每条重复环境、构建版本、Stopwatch频率、schema全集；Exception stack 单独去重附件，默认不保留任意 Message/ToString 中可能出现的 Secret。路径/堆栈/原始输出主导字节量，需payload上限。

## 7. EventCatalog / EventId / 兼容性

单一目录维护 code、MEL整数EventId、稳定英文名、版本、payload类型、delivery、隐私分类、解释资源、状态所有者、关联要求、预计频率、适用能力版本。启动把 catalog/hash/capability summary 写入 session。

区间：APP=1000、UI=2000、NET=3000、FS=4000、PLN=5000、PFL=6000、TRN=7000、RBC=8000、PST=9000、VRF=10000、RPR=11000、DIA=12000；例如 UI-001 对应 2001。**ID永不复用**，废弃留 tombstone；新增可选字段为minor，变义/删字段为major或新EventId。未知事件可展示/透传，不参与未匹配版本规则；未知 enum 保留raw，不强转Succeeded。

最小目录族：

- UI-001…009：UserActionObserved、CommandEligibilityEvaluated、CommandStarted、UiFeedbackExpected、UiProjectionChanged、UiFeedbackConfirmed、ActionCompleted、ActionRejected、ActionFaulted。
- TRN-001…：JobRunStarted/Completed、ObjectStarted/Completed、RetryScheduled/Started、ProgressObserved、PauseRequested/Observed/BoundaryReached/Paused、ResumeRequested/CheckpointLoaded/Resumed、StopRequested/Observed。
- RBC：ProcessStartRequested/Started/SpawnFailed/OutputObserved/OutputParseFailed/Exited/KillRequested/KillResult；**FileAttemptObserved，不叫FileCopySucceeded**。
- PST：WriteStarted/WriteSucceeded/WriteSkipped/WriteFailed、ReadFailed、ReceiptCorrupt、CheckpointLoaded。WriteSucceeded只表示写入API完成，另有durability标记。
- VRF：VerifyStarted、PlanValidated、SourceStatStarted/Succeeded/Failed、TargetStatStarted/Succeeded/Failed、SampleSelected、HashStarted/Succeeded/Failed、Mismatch、Error、Completed。统计Succeeded必须说明Complete/Partial，不把0/0当成功完成采样。
- DIA：ModeChanged、Backpressure、EventsDropped、StorageFailed/Recovered、SerializationFailed、AnalyzerLagged、SnapshotUnavailable、CoverageChanged、ShutdownIncomplete。

中文/英文从 catalog 展示层生成，规则仅依赖稳定ID和typed payload。外部Robocopy本地化输出不得绕过parser变成中文contains规则；parser声明locale/version/Unknown支持度。

## 8. Correlation / Causation / 时间与顺序

`Session → Action → Operation → ObjectOperation → PassAttempt → ChildProcess`，Persistence/Verify/Repair 为有parent的子operation；后台主动工作无Action也合法。Resume跨进程链接 previous session/run/checkpoint摘要，但创建新RunId。JobId/ObjectId保持原值，不改档。

ID显式传到跨线程回调/长期任务；AsyncLocal仅作便捷scope，不是唯一事实源。Dispatcher、native事件、进程stdout闭包捕获不可变context；dispose不能让晚到事件误挂到下一个动作。自动重试沿用operation、新Attempt；用户重试是新Action+Operation并Links旧incident。

Sequence在发布前分配，A分配后停顿可能晚于B入队；事件物理文件顺序仅称arrival order。Correlation引擎接受out-of-order，有界recent cache+因果待配对表，不无限等待缺号；丢失由显式计数/coverage标记说明，**全局Sequence缺口也可能是正常Verbose路由，不能直接判断Operational丢失**。Writer持久化水位用每分支接收序号/区间，不伪称全局连续fsync至某Sequence。

Monotonic只在同一session内比较；UTC跨VM对齐带ClockOffset/Uncertainty，绝不比较不同机器Stopwatch原值。检测时间跳变写ClockAnchorAdjusted，duration不回退。长睡眠/调试器暂停后的contract单独标记ClockDiscontinuity/ExecutionSuspended并恢复宽限。

## 9. User Action Trace 与 ControlId

正常只记录语义交互：连接、添加共享、选择/取消、准备、开始、暂停、恢复、停止、验证、修复、导航、打开报告/目标/日志、导出、Deep开关。TextChanged不记正文；Secret输入默认连Length也不记录，仅FieldChanged/ValidationResult（需防高频推断与告警轰炸）。

ControlId统一稳定表，例如 `Step1.Connect`、`Shell.Transfer.Pause`、`Step4.Verify`、`Diagnostics.Export`；绑定为显式AutomationId并复用到diagnostics selector。动态行用稳定control family + 脱敏item key；不拼完整路径，不以显示文本/列表index为ID。官方只要求兄弟唯一、不保证跨版本稳定，PCMig自行承诺versioned ID registry。

现有大多数动作是Click→VM，不强行改成ICommand。插桩只观察**原来已经执行的guard判断结果**，禁止为诊断多调用CanExecute delegate（可能有副作用），禁止修改RelayCommand的防重入/异常路径。

链路：Observed→Eligibility→Started→DomainRequestAccepted→StateObserved→FeedbackExpected→ProjectionApplied→FeedbackConfirmed→ActionCompleted。允许Rejected/NoOp/Failed/Canceled终止，无需伪造Domain调用。动作返回Task并不必然成功（现有VM可catch后返回）；终点须以实际结果分支记录。

`UI_ACTION_NOT_RECEIVED` 只在独立TestIntent（test action token）或显式Deep输入观测存在、控件可命中、窗口激活/布局上下文已知时启用。普通用户事后说“点过”，在没有输入证据时生成UserReportedSymptom而非证明HitTest故障。

Raw Deep：root/overlay分别按生命周期 `AddHandler(..., handledEventsToo:true)` 注册，记录Pointer/Tapped/导航键类别和ControlId，不记文本键、IME内容、敏感控件及其祖先内容。不得写Handled、Focus、Capture、路由；不用全局hook；记录“进入当前root的事件”，不保证覆盖disabled元素/另一个Popup/XamlRoot/系统标题栏。防重复事件，不每个Pointer创建Action。默认关闭、限时、可停止。

## 10. Expected Feedback Contract

Registry是一组版本化只读contracts：ActionKind、适用capability/ControlId、真实状态前提、预期事件DAG、immediate/deferred/external wait/optional/failure outcome、终止/取消/替代关系、延迟策略、所需证据等级。它描述应观察到什么，**不能执行命令或改CanResume**。

Tracker按 `(Session, Action, Operation, RunGeneration, ContractVersion)` 建项；单个后台PeriodicTimer/可取消scheduler，候选节拍100–250ms，仅待benchmark选择。上限限制pending数，按deadline桶/优先队列访问到期项，不为每项new Timer，不逐tick扫描全历史。UI回调不得驱动deadline时钟。

| 动作 | Immediate | Deferred/External | 取消/例外 |
|---|---|---|---|
| Connect | guard结果、Connecting反馈 | DNS/SMB各阶段完成或明确失败 | 已连接复用、用户改host/取消、源共享fallback |
| Prepare | 请求收到/忙态 | preflight→scan→plan→审核态 | 0选择/残缺扫描拒绝合法，用户review等待不超时 |
| Start/Resume | 受理/拒绝、运行反馈 | checkpoint/连接/对象活动 | 已运行、锁占用、权限失败应是显式terminal |
| Pause cooperative | RequestWrite结果+PausePending展示 | 观察请求、当前对象边界、Core Paused | 不对长对象设100ms paused要求；最后对象自然完成可替代Paused |
| Resume | 请求来源checkpoint、clear pause结果/新run | Core Running/首对象或无剩余完成 | 当前CanResume=false属于KnownContractConflict，不暗改 |
| Stop | cancel requested反馈 | process终止结果、receipt/state收尾 | 已完成竞态、无进程、正常取消不能报unexpected exit |
| Verify/Repair | gate通过/拒绝 | 分阶段统计/hash/重拷/复验 | 原始失败语义保留，不能把Task返回当PASS |
| Export | scope已确认/导出开始 | 文件封段、脱敏、校验、完成/失败 | 用户取消，空间不足，部分附件省略必须明示 |

Timeout数值分两层：设计预算（例如UI交互反馈目标）与测量窗口（P95/P99+调度宽限）。本轮不freeze毫秒阈值。实际pause边界、Robocopy /R /W退避、DNS每地址预算、外部等待都用已知reason。契约未安装、页不可见、viewport卸载、CPU饥饿/调试暂停、branch loss时结论为Inconclusive或KnownDeviation，不武断报binding坏了。

缺事件在watermark越过deadline且采集健康后才能定案；迟到事件更新同一Incident为Resolved/Corrected，不追加一片相互矛盾的卡。跟踪Action结束不等于全部Deferred expectation结束。

## 12. Flight Recorder

推荐**内存主环＋低频有界磁盘检查点＋触发冻结段**混合方案。只用内存无法满足kill后近尾证据；每条落盘又违背高频预算。

状态：Recording→Triggered/PostCapture→Sealed→PersistQueued→Persisted/Failed。Trigger时交换active段并pin故障前有限段，继续新active ring，不在业务线程复制整个ring。Post窗口由同一scheduler关闭；多个相近trigger合并窗口、incident多引用，限制同时冻结数、总pin bytes、最长post，防错误风暴无限延长。

容量同时限制event数、payload bytes、segment数、age；`N秒`是目标窗口不是保证，突发时实际pre coverage可短于N。manifest写Requested/ActualStart/End、覆盖秒数、overwritten/dropped、last checkpoint UTC/seq、post incomplete。

Checkpoints批量写rolling flight片段，kill前最多恢复已写检查点和已刷Operational，**无法恢复RAM尾巴**。低频checkpoint是否全量保留compact ring还是只落采样摘要由D2/D7 benchmark选择，不能宣称full raw黑匣子零损耗。磁盘慢则停止checkpoint并标degraded，不积压无限RAM。

触发：可信Error/Critical、rule SuspectedStall、feedback缺失、状态矛盾、诊断退化；可疑单条错误先去重/限速。ring正常覆盖是retention，不与drop混为一谈。触发/预窗口event refs以及Snapshot refs写incident。异常路径不等待post窗口。

## 13. Incident Analyzer 与 Incident Schema

在线Analyzer只读已规范事件，不读业务可变对象，不执行业务命令。历史Analyzer读取sealed JSONL，用同一RuleSet+虚拟时钟回放；detected-at与replay-at分开。

Incident字段：`IncidentId, Revision, RuleId, RuleVersion, Status(Open/Resolved/Inconclusive/Suppressed/Corrected), Severity, Type, SymptomCode, FirstSeen, LastSeen, DetectedAtUtc, SessionId, JobId?, ObjectId?, ActionId?, OperationId?, Expected[], Observed[], BreakPoint, RootCauseCandidates[], ConfidenceBand, ConfidenceRationale, EvidenceRefs[], MissingEvents[], EvidenceCompleteness, LossEpochs[], SnapshotRefs[], FlightWindowRefs[], RelatedIncidents[], UserFacingSummary, TechnicalSummary, SuggestedChecks[]`。

Confidence用ConfirmedObservation/High/Medium/Low/Unknown，并写前提，**不伪造87%统计概率**。确定事实如“Move返回112”；候选原因如“目标卷空间不足，可能为volume quota/空间变化”，区分错误域与物理原因。MissingEvent对象必须含contract、scope、deadline、coverage水位，不能把“没发现”当证据事件。

故障根/连锁症状按scope+rule family聚合：Network error导致Object retry、进度慢、UI stale，不弹四次同义根因。Analyzer保留有界active状态和recent evidence refs；完整历史在文件，可按需查询，不把2.1M文件建图。

### 13.1 Snapshot 契约与触发

SnapshotEnvelope包含SnapshotId、SchemaVersion、Session/Job/Operation/RunGeneration、RequestedAt/ObservedAtUtc与monotonic范围、provider/version、source event refs、Complete/Partial/Unavailable、截断/失败原因。不会用一个Timestamp伪装跨线程原子快照。

- Domain：从既有内存快照取phase、object/pass/attempt、估计/确证计数来源、pause/stop请求与实际ack、child process身份；不重读整个plan/receipt目录，不stat所有目标。
- VM：UI线程复制允许字段（IsRunning/IsPaused/CanStart/CanPause/CanStop/CanResume、phase/status code、当前job/generation），**不反射整个VM**，不复制密码/Username正文/整份集合。
- View：实际Push完成后关键控件值readback、ControlId、mounted/visible/IsEnabled、source版本；sentinel被阻塞则超时返回Unavailable，不跨线程读控件、不同步等待Dispatcher。
- Persistence/diagnostics：最后write/flush ack、artifact kind、loss counters/epoch、queue/ring quota、coverage模式；来源内存health，不为故障诊断再同步访问坏磁盘。
- Environment：session启动一次最小OS/runtime/应用版本、process架构、CPU/内存概况与版本化策略；机器名/IP/用户名按Personal处理，不扫环境变量全集。

触发为operation关键边界、incident、用户显式请求；按scope冷却合并、最多4份在途，每份256KiB候选上限。大对象只摘要和top-N异常；版本改变则丢弃旧generation结果或标Skew，不能拿半份A/半份B判状态矛盾。视觉截图是另一路L3显式授权能力，不是SnapshotProvider默认输出。

## 14. Rule Model（确定性且有反例）

模型：`RuleId/Version, SupportedEventVersions, Trigger, Prerequisites, ScopeKey, Exclusions, DeadlinePolicy, EvidenceRequirements, Severity, ConfidencePolicy, ExplanationResource, SuggestedChecks, SuppressionKey, RecoveryCondition`。

共用前提P0：相关event schema/capability可用；scope/RunGeneration匹配；未缺关键证据；采集/调度水位健康。超时规则P1另要求作用域存活、非expected wait、非debug/sleep；**page mounted只约束UI投影规则，不影响后台transfer/persistence规则**。P0失败输出EvidenceIncomplete，不作硬判；DIAGNOSTICS_DEGRADED本身依据独立health计数工作，不要求故障通道先恢复健康。

### 14.1 时间、置信度与排除的共用政策

时间策略 T0＝有明确结果的即时判定；Tui＝实测UI延迟分位数＋泵/动画适用宽限；Top＝对应operation的阶段预算；Tstall＝多采样窗口、满足最小有效样本数；Tboundary＝实际边界到达才评估；Tpersist＝真实writer分支结果，不凭调用耗时猜失败。数值由批准的配置版本随包记录，以下均不是已验证SLA。

严重度针对影响，不等于置信度：Warning可有确定观测，Critical也可能只有低置信候选。表中“高”仅为已满足P0与列出证据的观测结论；候选物理根因另评级。所有缺事件规则缺P0/P1时只报“证据不足”，而不是用超时给失败盖章。

| FILE_LOCKED | typed sharing/lock violation（32/33）＋读/写阶段 | 预期重试中暂不升级；Top | Warning/高“共享/锁冲突”；不能确定占用进程，建议外部工具 |
| TARGET_SPACE_EXHAUSTED | code112/39等与目标写相关，或既有空间快照佐证 | error domain/源或临时目录不同；T0 | Error/高的目标写失败；配额/实际free变化属候选 |
| SOURCE_CHANGED_OR_MISSING | 已有前后stat/version或实际读失败，源曾存在 | 预期排除、不可达被Exists吞成false；T0 | Warning/中；证据不足只说“不存在或不可访问”，不说源被删除 |
| PATH_POLICY_SKIP | 已有long-path/reparse/invalid/placeholder决策及数量 | configured skip正常→Info；T0 | Info/高事实，不当作文件丢失事故；无法识别时Unknown |
| PLAN_SELECTION_MISMATCH | 已提交selection摘要与plan映射不符，policy/exclusions/来源generation可复算 | 父子折叠、rootfiles、排除、残缺扫描、用户更新选择；T0 | Warning/中；只读比对，不另造Planner |
| PLAN_EMPTY_OR_INVALID | 实际plan对象数0、映射冲突/校验拒绝 | 用户未提交选择不算故障；T0 | Error/高或Rejected/Info，使用实际gate结果，不改已有空计划行为 |
| PERSISTENCE_WRITE_FAILED | WriteFailed/Skipped＋artifact kind/stage/code；旧值是否存在 | 被取消前未开始不是失败；Tpersist | Receipt/plan风险为Error，state view skip为Warning；高，不把返回当成功 |
| PERSISTENCE_READ_CORRUPT | 明确deserialize/read异常或receipt corrupt分支 | 文件不存在可为首次运行；T0 | Warning/Error按artifact；可读receipt重建是独立事实，不断言恢复已成功 |
| PAUSE_NOT_ACKNOWLEDGED | RequestWriteSucceeded，缺CoreObserved/Paused，scope在跑 | cooperative等对象边界；Tboundary之后Top；Immediate单独预算 | Warning/中；区分请求未观察和等待合法边界，不要求瞬时停进程 |
| RESUME_NOT_EFFECTIVE | Resume受理、checkpoint已载、缺Running/NoRemaining/Failed | 当前CanResume拒绝不启动此规则；连接/锁等待；Top | Warning/中；不修改pause文件或主动重试 |
| STOP_NOT_EFFECTIVE | cancel/kill requested，终止ack缺失，进程标识同一 | 已自然结束、进程ID复用、收尾IO、正常关窗；Top | Error/中；“停止未确认”而非“kill失败” |
| VERIFY_EVIDENCE_INCOMPLETE | stat partial/hash failed/source不可达；或contract要求内容抽样却零有效sample，而业务report OK | 合法空源与完整0/0须另有完整性证据；L1本就不hash，显示证据等级说明而非仅因零sample报事故；T0 | Warning/高“不足以证明内容一致”；不改OverallPass或写回report |
| VERIFY_MISMATCH | 真实Count/Bytes/Hash mismatch结果 | 不把HashFailed当HashMismatch；T0 | Error/高观测差异，样本通过不外推全量 |
| REPAIR_SCOPE_OR_RESULT_UNCERTAIN | repair目标来源缺失/实际purge失败/复验缺失 | no targets合法NoOp；用户取消、retransfer失败；Top | Warning/Error；事实/候选分开，绝不自动扩大全量修复 |
| DIAGNOSTICS_DEGRADED | 任一loss、writer失败、序列化失败、analyzer lag或coverage关闭 | intentional filter与ring正常覆盖不同类；T0 | Warning；critical lost为Error，高；关联失效的rule降级 |
| PREVIOUS_SESSION_UNCLEAN | startup发现marker无clean completion且该session进程不存活 | 另实例仍活、PID复用、metadata损坏、磁盘失败；T0 | Warning/中“上次未确认正常关闭”，不能认定crash原因 |

### 14.3 必须覆盖的反例与回放

- 2TB大文件30分钟无新FileAttempt行、/Z目标长度正在变化：不报确定停滞；stdout静默不等于IO停止。
- IPC$失败但源共享可读：只给发现能力降级，不报连接失败；DNS失败后地址fallback成功同理。
- 合作式Pause时当前对象未结束：只跟踪PausePending；自然完成整个Job是合法替代终点。
- UI batching合并10次snapshot只上屏最后一次：中间projection缺失是设计行为；terminal/即时契约不能被普通合并抹掉。
- Task Picker preview不等于Adopt/Loaded；只有预览不得期待Domain任务载入。
- Debugger暂停、Windows睡眠、writer分支丢失、页面关闭：缺事件不能升级高置信事故。
- 目标空间充足但用户配额耗尽；源不可达导致0/0：分别保留code上下文和不完整证据，不能照UI文案归因。
- Run A迟到事件到达Run B：只能更新A，不能让B结案；已Corrected的incident保留revision审计。

每条规则有positive、negative、loss/late、取消、generation切换五组最小fixture；使用虚拟时间，无真实Thread.Sleep。规则成熟度分Experimental/Validated，未经三VM/规模场景校准的启发式始终显示Experimental。

## 15. Persistence 与格式选型

推荐Operational/Incidents/Metrics JSONL（UTF-8、无BOM、每行独立对象），不做巨大JSON数组。`.ps1`的BOM纪律与此无关。session级单写者、大小滚动，按session/day划分目录；`events-0001.jsonl`、`metrics-0001.jsonl`、`incidents-0001.jsonl`、`flight/`、`snapshots/`、`session.json`、`catalog.json`。

每段封段manifest记录length/SHA256/event count/seq范围/时间范围/partial标志；active文件crash后忽略并保留不完整末行，完整但非法行标CorruptRange，不吞成“无事件”。每行长度上限，防恢复时单行OOM。

JSONL：写路径简单、崩溃前完整行可读、离线兼容；代价为查询scan，需要后台建立可重建稀疏索引（Job/Operation/时间→segment/offset，非每文件index）。SQLite：事务/索引成熟，但WAL/checkpoint/锁/重复序列化和写放大增加共享磁盘负荷；**本轮无实测证据证明更好，故不作在线store**，将来可作为离线重建索引。二进制/EventPipe：深性能高效，但不适合唯一语义存档；无需自创binary协议，内存compact结构与导出JSONL分离。

Retention同时size/count/age/total quota，候选组合必须D2 benchmark后freeze。清理只在专有diagnostics root内，拒绝reparse穿越；不清理Job/Receipt/raw既有日志或用户导出zip。active session/incident pin/export lease优先保护，但总硬上限最终生效：优先停止新采集/导出，释放或取消lease后再删，**不能在活跃reader下强删文件**。无法腾出空间时标StorageQuotaExhausted；证据被evict必须明确标记，不能“pin永不删”撑爆磁盘。

首版目录推荐`%LOCALAPPDATA%\PCMig\Diagnostics\<SessionId>`，使用当前用户权限，避免新要求管理员；企业如选`%ProgramData%`须明确ACL和多用户可见性，不能继承宽权限后称安全。fallback仍为同用户受限目录，若同卷满并不能解决空间问题，最多保内存health。预分配有限reserve计入总quota，导出临时文件也单独计额/校验可用空间；磁盘可用空间检查本身是近似，不能保证后续写成功。

## 16. Channels / backpressure / 自身健康 / durability

MPSC有界Channel：SingleReader=true、SingleWriter=false、AllowSynchronousContinuations=false。Operational配置Wait，但**生产调用只用TryWrite，不await WriteAsync**；满即false，进入明确溢出路径。Verbose允许DropOldest/DropWrite，使用.NET8 `CreateBounded(options, itemDropped)`原子计数；drop模式TryWrite成功不代表无事件被淘汰。

资源预算：event个数之外有payload bytes上限；Metadata/stack/raw截断先于入队。Channel原生只限个数，byte预算必须由独立原子reservation实现，入队失败/淘汰/消费完成均只释放一次；fan-out共享载荷与复制载荷分别记账，不能以三个分支都“4096条”隐含三倍内存。itemDropped callback仅计数/释放budget，不调用外部sink。每条错误字符串/Metadata key/value及stack总长另有硬上限，不允许一个event占满整个队列。满队列规则：

1. Verbose先削减采样并计数；metrics使用latest聚合，不一测量一事件。
2. Operational满：尝试预留有界overflow/reserve；若仍满，记录lost count及时间/seq范围摘要，置DiagnosticsDegraded。**不能静默DropOldest**，也不声称永不丢。
3. Critical：专用reserve + 预分配最小emergency slot；专用后台writer优先，限速聚合重复事故。全部满仍可能丢失，sticky atomic lost-critical必须可见。
4. 独立emergency worker尝试受限fallback文件，主路径失效才用；fallback不在业务线程做阻塞写。Windows文件IO卡住不能靠CancellationToken保证硬时间上限；一个故障writer不反复spawn新线程/Task重试。
5. Analyzer/UI分支满分别记loss/lag，禁止形成“writer已成功所以rule证据完整”的假象。Writer卡住不阻断Analyzer，Analyzer卡住不阻断Writer。
6. Health使用独立固定计数＋最后故障槽，定期summary；SelfLog不能再写回同一Serilog/Hub，避免递归风暴。

必备：Produced/Accepted/Written/Dropped/Filtered/Coalesced（口径独立），QueueDepth、WriterLatency、FlushLatency、FileBytes、RingUsage、UiPending、SerializationFailures、StorageFailures、AnalyzerLag、CriticalLost、LastSuccessfulFlush。按分支和DeliveryClass低基数拆分；UI最新健康状态即使主日志坏了也可读。

Delivery诚实边界：

| Class | 正常策略 | 可承诺 | 不能承诺 |
|---|---|---|---|
| Verbose | bounded/drop/批量 | 已记录事件可识别丢失窗口 | 每文件/每输入完整 |
| Operational | bounded/保留优先/批量写+周期flush | accepted/written/flushed水位分别可查 | TryPublish成功即断电持久 |
| DurableCritical | reserve/优先写；writer请求FileStream.Flush(true) | **仅收到flush成功ack**才标DiskFlushAcknowledged | 无ack、硬断电、控制器缓存故障仍零丢 |

DurableCritical是交付目标类，不是同步成功保证。可显式 `RequestFlushAsync(deadline)` 给关闭/导出路径，业务线程不等待。Stream.Flush/FlushAsync通常只到OS，与Flush(true)分开记录。batch interval/size/critical group flush窗口均待测；shutdown budget到期仍按原失败语义退出，写ShutdownIncomplete尽力而为。

## 17. Metrics

推荐System.Diagnostics.Metrics.Meter（BCL）＋本地MeterListener/快照采样器。listener可能在记录线程运行，callback仅累加/聚合、不得IO。新业务指标不用EventCounter；.NET8 runtime现成EventCounters可以由专家工具收集，不能假定较新.NET所有runtime Meter在8.0已有。

- Counter<long>：真实字节/文件累计、attempts、drops、errors；近似进度允许回冲，**不要往Counter加负数**，用ObservableGauge并写Estimated来源。
- ObservableGauge/UpDownCounter：当前吞吐、objects/process active、queue depth、ring占用；速率由delta+monotonic时间推导。
- Histogram<double>：feedback/dispatch/write/flush latency，单位s或ms全目录统一。
- 进程采样：WorkingSet64、TotalProcessorTime差/墙钟与processor count定义CPU%；GC.GetTotalAllocatedBytes差、GC.CollectionCount、可用GC信息。GC pause为已有API最近/累计口径或Deep trace，不捏造连续精确停顿。
- 指标族：transfer.bytes/files/objects、robocopy.process、scan.files、verify.files、ui.feedback/dispatch、diagnostics.*、process.*、gc.*。

允许tags：category、outcome、pass、deliveryClass、storageKind、rule family；禁止JobId/ObjectId/Path/ActionId/User/IP作为长期Meter维度。单Job筛选从事件/诊断快照查，不增加series。time-series数量=各维度组合乘积×histogram buckets，应预算并限流未知tag值。

## 18. ActivitySource

采用少量长期source：`PCMig.Core`、`PCMig.UI`、`PCMig.Diagnostics`；Action/Connection/Scan/Plan/Transfer/Object/Robocopy/Persistence/Verify/Repair是**span名称**，不用每operation创建ActivitySource。

PCMig稳定ID始终存在；`StartActivity()`在无listener/采样关闭时可null，TraceId等为空合法。`IsAllDataRequested`后才构造昂贵tags；不在Activity.AddEvent循环塞百万文件；ID作为Trace属性可以高基数，但不作为Meter tags。结束/失败/canceled scope完整；重试子span带attempt；长期等待可以事件描述，不为每轮poll建span。

目前不引入Collector/云/OTLP；若将来安装OpenTelemetry SDK，由composition root AddSource/Meter/ILogger provider接走，source单例及ID规范不变。Activity/W3C span和诊断tree通过OperationId关联，两套互补，不互相冒充。

## 19. EventSource / EventPipe / DiagnosticsClient 与 Deep Trace

**首版不内置自动EventPipe采集器**。保留可选PCMig EventSource桥（粗粒度事件、无私密payload），专家按明确同意使用外部dotnet-trace/dotnet-counters；UI Deep Trace首先是应用自己的有界高详细度记录，不偷换成系统trace。

| 技术 | 可得证据 | 不能替代/部署边界 |
|---|---|---|
| EventSource | typed事件、与ETW/EventPipe互通；IsEnabled后再构造payload | EventId固定且参数顺序匹配；不自动产生Action/Job语义；不无限重复Hub内容 |
| EventPipe | 托管runtime、自定义EventSource、GC/线程等事件，.nettrace | 不等于Windows kernel/disk/SMB原生全景；开销与provider/stack/采样强度相关 |
| Microsoft.Diagnostics.NETCore.Client | 外部工具以PID连接.NET诊断端口，start/stop EventPipe等 | 权限、同用户、diagnostics被关闭、退出竞态都可失败；self-attach本轮未验证，不作为常驻核心依赖 |
| WPR/WPA | ETW系统/进程/CPU/磁盘等profile，分析.etl | 可能需管理员/ADK/权限，时间和文件配额明确；不能无授权自动启用 |
| ProcMon | 文件/注册表/进程线程操作、返回值与stack | 对百万文件开销/文件量巨大，必须PID/path过滤及短窗口；系统软件许可与目标OS另核 |

.NET8 Windows诊断端口为named pipe，通常同用户或更高权限；`DOTNET_EnableDiagnostics=0`时专家工具不可用，应解释而非偷偷改环境。禁止为启动采集设置默认startup suspend导致产品等工具才能启动。

Deep开关明确：范围（当前session/job/action）、类别、最长时长、最大字节、采样率、剩余时间、敏感风险、开始/停止/到期事件。候选默认60秒、最大5分钟与128MiB仅是D2待测配置。超过时限/配额/低磁盘/用户退出自动结束，mode变化不改传输。Provider列表、工具版本、权限结果、丢失统计随包保存；.nettrace/.etl/dump为**可能包含秘密且无法保证结构化脱敏**的独立附件，默认不导出、不自动上传。

## 20. Sensitive Data Redaction 与数据分类

分类从typed payload定义开始，不靠最后正则“洗日志”。所有sink（ring/JSONL/Activity/Meter/截图/emergency/导出）共用policy version。

| 分类 | 示例 | 正常记录/导出政策 |
|---|---|---|
| Public | EventId、phase枚举、版本、匿名错误码、数量/时间 | 允许；环境指纹仍按最小必要 |
| Personal | Windows用户名、主机/IP、路径、文件名、任务备注 | 默认路径token/用户名别名、HMAC关联；导出再次统一映射；明文需逐项同意 |
| Secret | SMB口令、token、认证头、连接串密码、剪贴板/PasswordBox内容 | **禁止发布**；不能hash后记录，不捕获长度/键值/异常Data；与业务对象分离 |

PathRef默认 `{role, rootKind, rootAlias, pathToken, extensionClass?, depthBucket?, keyId, scope}`；extension也可能敏感，按白名单粗分。规范化需明确大小写/UNC/root/末尾斜杠语义，不访问文件系统、不ResolveLink；完整Path可用于用户本地显式展开的独立高敏感显示，不自动写回日志。

HMAC-SHA256使用随机key，不能使用无盐SHA256对可猜IP/路径；不凭“hash不可逆”宣称匿名。session内关联key保存在受限权限的本地状态（如DPAPI保护），导出用**每包新key**重映射，manifest只带KeyId/Scope不带key。不同包默认不可连结；跨包需要用户显式选择受控支持会话。Secret不走这个机制。

推荐首版用BCL HMAC及小型明确Redactor接口，Microsoft.Extensions.Compliance.Redaction作为可选实现/比较对象，不为它引入整套DI。其8.0.0包具有net6兼容资产，但官方当前HmacRedactor示例与实验API状态/版本不能直接映射到8.0.0；采用前必须检查选定包API/analyzer警告、许可、传递依赖。任何redactor异常默认**丢弃该敏感字段并计数**，不回退原文。

异常：保存Type、HResult、明确NativeErrorCode、规范化stack frame摘要；Message/ToString是未受信任文本，可能包含路径/参数/secret，只能经allowlist转换后存。不要捕获Exception对象到长期队列。Process args按白名单记录 `/MT`、pass、retry等，source/dest/fileList为PathRef；不直接拷贝命令行。

旧raw Robocopy日志、poc-startup、Job/Receipt、Verify报告默认不原样装包。先转换诊断DTO，只导出必要事实；旧文件可能已有个人信息，方案不能追溯宣称它们已脱敏。redaction用人工合成canary测试，不读取实际settings/历史凭据作测试集。

## 21. Crash / UnhandledException / Unexpected Exit

在composition root尽早建立session目录、启动marker、应用/OS/runtime版本、process-start身份；创建失败进入NoOp＋内存health，不因诊断目录不可写阻止产品启动。marker和clean写入也可能失败，恢复时必须带StorageHealth上下文。

- WinUI `Application.UnhandledException`：最小非抛capture，**保留当前不设置Handled的策略**；诊断不将未知异常吞掉以“保证继续”。
- AppDomain.UnhandledException：限额最小数据，进程终止阶段不做大图快照/异步导出，不保证回调完成。
- TaskScheduler.UnobservedTaskException：仅补充迟到线索，不能替代await/catch；触发受GC影响，现代.NET默认不因此终止。显式后台任务必须由owner观察exception，不能用全局事件当监控。
- FirstChanceException：默认关闭；throw高频、含大量预期异常与Secret；Deep也只限类型/采样摘要，不无界ToString。
- StackOverflow、FailFast、native AV、强杀、断电、系统崩溃不保证托管handler执行；仅能恢复先前持久证据。外部dump/Windows Error Reporting是单独授权路径。

正常关闭：标Closing→停止新UI/Deep订阅→request bounded diagnostic drain→封段/clean marker（结果如实）→沿用既有StopUiRefresh/资源清理/Environment.Exit规避路径。未来精确顺序必须检查UI线程死锁和当前关闭约束；不在ProcessExit做依赖UI的await，不调用Serilog无限Dispose阻住关窗。若没有完成flush就不得写“全部诊断已保存”。

下次启动：只读检查previous marker、process身份（不能只看PID），解析完整JSONL行、列出tail损失/未封段。提示“上次正常关闭未确认”，提供导出，不把用户kill、诊断写失败、应用crash混成一个根因。active多实例各有session目录，禁止共享active文件竞争。

```text
sessions/<id>/session.json
sessions/<id>/events/*.jsonl    已脱敏Operational切片
sessions/<id>/incidents.jsonl
sessions/<id>/metrics.jsonl
sessions/<id>/flight/*.jsonl    触发窗口及loss信息
snapshots/*.json                DTO，不是原业务存档
attachments/                   明确同意的高敏感附件，默认无
checksums.sha256                文件相对路径、长度、SHA256
```

流程：用户选择范围/脱敏级别→估算字节和敏感附件→请求active segment封段/一致快照→以lease固定有限只读集合→后台流式redact/zip→验证条目/长度/哈希→临时`.partial`原子改名。取消/失败只清理本次专用临时目录，不清用户选择的已有zip；不覆盖同名文件，选择新名。

一致性是**每附件时点+cutoff watermark**，不是暂停业务的全局事务。snapshot generation不一致要标Partial/Skew。不能为导出锁住整个Job，也不能再次遍历2.1M迁移文件算hash；仅对所导出的诊断小文件算hash。无存储时允许有限内存health导出，明确缺什么。

默认zip无需网服务；传输通道由用户决定，工具不上传。标准zip不是加密存储，界面明确提示；敏感附件可拒绝加入或另走组织加密流程，不自创加密zip。归档导入将来按不受信任处理：防ZipSlip、绝对路径/reparse、压缩炸弹、巨行、重复名字、数量/总量上限；不执行脚本/自动打开URL。SHA256仅完整性校验，不是签名/防篡改证明。

导出摘要必须可单独阅读：用户动作、预期、观察、断点、事实、候选与证据引用、排除项、置信依据、采集缺口、建议人工检查；不要求接收方装PCMig或云Collector。

8. 高级日志：过滤EventId/category/severity/operation、复制脱敏行、分页查询；不每次过滤重扫全部历史到UI线程。

## 25. 性能模型、2.1M文件与候选预算

以下是**工程预算候选，不是实测结果**。先保证增量随对象/时间增长而不是每文件持久事件增长。

### 25.1 工作量与存储算式

设文件数F、迁移对象数O、运行秒数T、采样周期S、每对象生命周期事件K、平均事件字节B：Operational规模约 `K×O + T/S + actions + errors聚合`，而非`K×F`。如果每文件600B，2,100,000文件一轮就是1.26GB十进制，三份约3.78GB，尚不含JSON/object/stack开销；因此正常不得逐文件记录永久成功事件。

文件attempt路径：已有parser产生的回调可增计数/更新latest、选择性采样compact ring；不能再格式化两份路径字符串/hash每个文件/创建Guid/Activity/Task。采样决定先于昂贵payload；error做signature限速与first/last/count，保留代表例和truncated标记。某些选择策略仍每文件做原子增量，需要benchmark，不宣传零成本。

内存估计：`Σ(queueCapacity×(struct/reference+bounded payload)) + ringBytes + pinnedBytes + incidentState + snapshots + viewerCache`；GC堆、native buffers、ArrayPool租借高水位另算，不能用“事件数×JSON大小”当真实内存。

### 25.2 用于Probe的初始配置（待批准校准）

| 资源/指标 | 候选值或目标 | 失败处理 |
|---|---|---|
| Operational ingest | 4096 events，同时≤8MiB有效payload | reserve/loss ledger；绝不block业务 |
| Critical reserve | 256 events，固定小payload | emergency slot、sticky critical-lost |
| Verbose ingest | 8192 events，同时≤16MiB | drop/采样提高、真实drop计数 |
| Flight ring | 32MiB＋最多2个冻结窗口，总pin≤32MiB | 合并/截短/evict并标coverage |
| Analyzer | pending actions≤1024、active incidents≤256、每incident evidence refs≤128 | 关闭新缺事件判定，summary＋degraded |
| Snapshot | 每份≤256KiB，总inflight≤4 | 截断/拒绝、partial，不clone全部plan/file list |
| 全局payload预算 | 正常模式（含各fan-out分支）≤64MiB；含pin/export峰值≤128MiB | 这是payload不是整个进程堆；各子配额共享此上限，不能各自同时耗尽后无总闸门 |
| Viewer | 内存事件行≤2000，后台页查询；指标每series≤600点 | 分页/降采样，bounded UI批量 |
| 持久盘 | 初始总quota512MiB，段16MiB，7天上限；同时满足取最小 | 背景清理诊断目录，优先保事故但不突破硬上限 |
| writer batch | ≤64KiB或250ms，Critical优先；checkpoint候选2秒 | 性能/损失窗口A/B后定；不承诺定时器准点 |
| 正常采样 | metrics 1秒；UI健康1秒且最多1个inflight sentinel | 忙时降采样，不积压Dispatcher工作项 |
| Hot publish候选目标 | 标量发布P99≤50µs；OFF路径不构造payload | 失败先减payload/分支，再降低能力，不调整迁移线程数 |
| 端到端候选目标 | Operational相对同条件OFF吞吐下降≤2%，＋Flight≤5% | 噪声区间重叠则不声称达标，实际阈值由评审批准 |
| CPU/内存候选目标 | 正常诊断增量CPU≤1个百分点（机器归一口径）；steady heap增量≤96MiB | 高峰pin/export单列；禁止隐藏到native内存 |
| UI候选目标 | 诊断批量应用P95≤4ms，交互反馈P95≤100ms、P99≤250ms | 不是合作式暂停完成SLA；与PMML动画时长分开 |

环32MiB在600B/event理想payload约5.6万条，真实对象额外开销会缩短；吞吐1万event/s也只有数秒前史。窗口秒数由实际速率决定，不能同时承诺固定容量＋任意负载60秒全量。

quota为新诊断目录，不包含既有Job raw日志；现有Serilog文本/JSONL默认1GB封顶且日滚动未启用size roll时可能提前停止收新事件，须在后续授权改动里显式治理。**不得把改变legacy最低级别/停写raw日志藏在性能优化中**：需专门批准，并对照等效baseline，否则测出的“提速”不能归功新架构。

### 25.3 CPU / allocation / IO 预算的使用方式

估算CPU负载用`Σ(eventRate_i × producerCost_i) + Σ(acceptedRate_i × consumerCost_i)`，消费含redact/serialize/rules/IO协调；以core-seconds换机器CPU百分比，不能把100µs乘样本数后当整个进程开销。假设1万次/秒每次10µs，仅producer已占0.1 core；这解释为何50µs P99仅为发布尾延迟上限，不可套到每文件高频路径。

初始目标：OFF标量路径0额外分配、无payload构造；未采样的高频文件回调仅计数/latest引用；采样后分配按实际accepted rate统计。普通Operational事件候选平均序列化≤1KiB、单条≤8KiB；异常附件单独限额。仅1Hz平均1KiB样本一天约84.4MiB，7天约590.6MiB，已超过512MiB候选quota，故**age与size同时生效、保留天数不保证**，可按重要性降低采样/聚合，实际保留覆盖必须显示。容量评估还要加现有raw日志与源/目标盘竞争，诊断写本地另一卷只是可选部署，不是假定环境。

### 25.4 正式benchmark矩阵（本轮不执行）

同一Release x64、同等缓存/网络/文件集、固定Robocopy参数/既有日志配置；顺序交错，报告重复样本/噪声/置信区间。模式：新诊断OFF、Operational、Operational+Flight、Deep、UI打开/关闭、导出并行；OFF仅关闭新诊断，不偷偷关既有日志。

数据：小样本功能、混合中等文件、单大文件、海量小文件、**≥2.1M文件**；本地SSD、SMB代表链路；冷/暖分开。记录吞吐/总耗时、PCMig与robocopy CPU、working set/private bytes、alloc/s、GC、UI latency、IO bytes/IOPS、drops、export尾延迟、磁盘空间；单点MB/s不足以验收。

纯独立microbenchmark先检验typed publish/序列化/Channel/ring/redact成本；不能替代真实迁移。大规模/三VM正式验证位于Stage B之后，前期只有限额合成事件压测，不冒充业务完整性验收。

## 26. 故障注入与 fail-open

设计原则：诊断不能改变任何业务return/throw、取消、pause文件、线程数、retry、Receipt和Verify结果。传入诊断订阅方异常在观察边界吞并health计数，但**业务异常不能被诊断catch吞掉**。logger初始化失败→NoOp，故障的诊断组件隔离后可恢复，产品继续。

| 注入 | 验收事实 |
|---|---|
| diagnostics目录拒绝/磁盘满/卷移除/locked file | 业务路径与OFF对照等价；writer退化、内存有界、恢复不无限重试 |
| writer长期阻塞/极慢flush | producers不等待IO；Analyzer仍工作；超过预算loss有记录；关闭不无限等 |
| ingest/analyzer/viewer各自队列满 | 各分支loss可区分；缺事件规则不高置信误报；不误把ring覆盖算丢队列 |
| serializer遇超长/未知/非法字符payload | 裁剪或拒绝该事件，继续后续；不回退Secret原文 |
| redactor抛异常/策略缺失 | 字段被丢/记录policy failure；Secret canary不出现于任何输出 |
| analyzer规则抛异常/超时 | 单规则隔离、版本标degraded；不得杀writer或UI |
| UI dispatcher拒绝/页面销毁/切job/动画中断 | 无旧generation污染，无后台控件写，无subscriber泄漏 |
| 强杀/FailFast/损坏JSONL末行 | 仅恢复已持久完整行；unclean提示诚实，clean marker不造假 |
| monotonic模拟/UTC跳变/sleep/late乱序 | duration稳定；P1抑制；同incident修订非重复轰炸 |
| error storm/trigger storm/pinned多窗口 | 总RAM/盘quota保持；合并限额，coverage变短可见 |
| 导出中关窗/取消/盘满/恶意归档 | partial不冒充完成、无覆盖无路径穿越、租约释放 |
| KillRequested后PID复用 | 依据PID+start identity，不能错误归因或操作新进程 |

Fail-open不意味着运行时任何故障都能续命：OOM、栈溢出、进程级native崩溃无法可靠隔离；因此前置配额、无无限重试、无任意callback和低风险payload比全局catch更重要。首版无常驻sidecar；若后期必须抵御写盘死锁/主进程挂死，要单独评估外部采集进程，不在当前范围偷加服务。

```text
Core ───────────→ Diagnostics.Abstractions ←──────── Diagnostics runtime
  ↑                                                        ↑
WinUI / CLI / WPF composition roots ────────────────────────┘
WinUI viewer → read-only IDiagnosticQuery / IIncidentFeed
Diagnostics runtime ↛ Core / WinUI / business commands
```

类型职责：`IDiagnosticPublisher.TryPublish(in ...)`只报accepted；`DiagnosticContext`不可变；`IReadOnlySnapshotProvider`返回已复制且限额DTO；`IIncidentRule`纯事件状态归约；`IClock`monotonic/time；`IFlushCoordinator`生命周期路径可await；`IRedactor`classification→safe value；`IStorageHealth`是独立内存状态，不靠logger访问。

复杂payload通过强类型方法/union设计，不能为`in struct`名义而里面放大量object/params boxing；线程安全/对象池所有权写清。一事件广播多分支时不可回收共享buffer直到引用结束；首版优先不可变限额数据，未测前不用unsafe自制无锁环。ring可以短临界区，但不能宣传绝对lock-free；writer/serialization从不在锁内。

Core默认NoOp用于旧shell兼容，装配根显式提供publisher。已有方法签名/测试构造的兼容设计与项目引用必须先走D1探针，不在一次改动中全仓替换ILogger。产品文件每步改动前满足备份/冻结授权。

## 33. 决策登记、未决项和回退

已推荐：JSONL为语义事实主存；混合Flight；typed publisher＋独立业务ID；低基数Meter；Activity可空；无AI；保留Serilog legacy；无SQLite在线写；无常驻EventPipe/Collector；明确loss/fail-open；默认脱敏；两项目隔离依赖。

需用户批准：D1可触及的冻结文件范围；正常记录是否默认Operational+Flight或仅Operational；实际磁盘目录/ACL及quota；Deep默认/最大时长；UI入口；是否未来治理legacy Debug/UNILOG量；公司支持包隐私标准；性能预算与代表硬件。文档给候选推荐，不把待测参数变既定事实。

回退设计：composition root可切NoOp、按组件关闭rule/viewer/flight，无业务存档迁移；旧业务继续原日志。关闭诊断不能卸载正在执行的业务或改其CancellationToken；raw已有文件与新诊断目录分开，回退不自动删除证据。catalog/schema版本只增；老viewer未知字段可展示而不执行不兼容rule。

最大风险：

- 把观察式系统写成“第二套业务状态机”，试图自动补pause/resume或根据诊断改verify PASS，导致事实权威冲突。
- 热路径为了“全链路”每文件建字符串/Guid/span、反复hash路径、多份队列/序列化，放大2.1M文件负载。
- 将absence当事实、用中文字符串猜错误、忽略collector loss，生成看起来确定但错误的根因。
- 红线之外：即使diagnostics fail-open，新增第三方库/进程hook/崩溃handler仍可能改变运行；需分阶段小改验证。

## 35. A–O 明确答复与最终建议

### A. 是否必须引入 Serilog？

**不是新引入，也不是架构必需**：当前已依赖Serilog4.1/File6/Async2.1/Compact3。保留避免无关大改；新因果事实走typed publisher与唯一规范writer。MEL8源生成是可选普通日志API，不为了“现代化”全仓换ILogger或引入Host。重复序列化/双向回采必须禁止。

### B. Operational 采用什么格式？

**UTF-8 JSONL分段**，稳定schema/EventId、单写者、大小/时间/总quota管理、partial尾行恢复、可重建稀疏索引。不是巨大JSON数组，不靠Serilog Message解析因果。SQLite暂不作在线主存。

### C. Flight Recorder 用内存还是磁盘？

**有界内存环＋低频有界磁盘checkpoint＋事故pre/post冻结段**。内存性能好但kill丢尾，磁盘检查点提高可恢复性但有额外IO；实际窗口/丢失范围要写manifest，参数待测。不是每条raw都保证存下来。

### D. 怎样判断“点击没反应”发生在哪？

依次检查独立意图（可选）→语义Observed→Eligibility→Started→Domain受理/失败→state observation→VM→真实View readback→contract ack。每层有Action/Operation/generation/版本引用。未看到Observed且无独立意图，**不能证明点击被丢**；只能报告用户症状/证据缺失。缺事件判断还必须采集健康、deadline成熟、排除合法等待。

### E. 210万文件会多大开销？

本轮**没有实测，不能给实际百分比保证**。每文件600B已是1.26GB/轮，拒绝正常逐文件永久记录；正常成本主要随对象数/采样时间增长。热路径先采样再构造payload、只累加/更新latest；§25给出RAM/CPU/延迟/吞吐候选预算和OFF/Operational/Flight/Deep对照矩阵，D7真实规模验收之前不能称达标。

### F. 队列满怎么办？

Verbose丢弃/降采样；Operational与Critical用有界预留及独立emergency slot，全部耗尽仍可能丢，必须sticky loss/范围/health可见，相关absence规则降级。生产者只TryWrite不等磁盘；不能用blockWhenFull来保护日志而拖死迁移。两个reader不当广播。

### G. Critical 怎样保证持久？

专用reserve、优先writer、限速合并与明确flush(true) ack；只有ack后才称DiskFlushAcknowledged。**不承诺进程强杀/断电/硬件故障下零丢**，也不把TryPublish/FlushAsync成功当物理稳定落盘。硬件极端保证需独立设施，非本系统能力。

### H. 怎样避免规则误报？

capability版本、scope/generation、单调时间、P0/P1证据完整性、合法等待/页面生命周期/采样丢失排除、迟到纠正、已知偏差登记、每规则反例fixture。启发式标Experimental；timeout经真实延迟分布校准，不一律100ms或45秒。

### I. 事实与根因候选怎样分开？

Incident有Observed facts（引用具体event实例）、Missing（contract/窗口/coverage）、RootCauseCandidates（支持/反证/未知）、ConfidenceRationale、NextChecks。code112是操作失败证据，VM关机/杀毒影响/网络故障通常是候选；不给伪概率和未经证明“根因已定位”。

### J. EventPipe 要不要内置？

**首版不强内置**。Activity/Meter/EventSource API留扩展，专家显式限时外部dotnet-trace；.NETCore.Client/self-attach、权限/失效/配额需独立Probe。WPR/WPA/ProcMon提供不同层证据，不自动安装、提权或附加。

### K. 怎样脱敏？

typed字段Public/Personal/Secret分类；Secret不入入口；Personal默认token/HMAC，导出每包重映射，不导出key；所有sink包括ring/Activity/emergency一致。旧raw/Exception.ToString不原样zip。trace/dump/截图默认不导出且不能保证通用脱敏；redactor失败丢字段，不回退原文。

### L. 怎样确保诊断失败不影响业务？

NoOp默认、try-publish、有限数据/队列/状态、独立writer/analyzer/viewer、诊断异常隔离、自身health不递归、关闭等待有界、不新增SMB探测/目录遍历；保留业务throw/cancel/state/Receipt口径。以OFF/ON和故障注入验证等价；无法保证OOM/native crash后继续，必须预防资源失控。

### M. UI 投影证据怎么取得？

三层：**L1 Domain/VM观测**（实际状态与source ref）→**L2控件投影readback**（在真实PushFooter/PushState之后，UI线程读取关键Text/Value/IsEnabled/Visibility、source generation/version、mounted状态）→**L3独立视觉/自动化测试快照**（按需明确授权）。L2同写者自ack只能证明赋值/读回，不证明屏幕像素或用户看到；L3也有遮挡/采样时间限制。正常用L1+L2，L3不常驻截图，Secret控件永不采集。

### N. 当前最大的盲区是什么？

**Click到Core到实际View没有可关联证据链**，尤其Click直调VM、VM值更新不等于控件已投影；同时一个具体高风险盲点是**WinUI未接JsonStateStore.OnWarning，已存在文件写失败可返回而不代表持久成功**。其次Verifier检查不完整与业务OK无法区分。先补观察证据，不擅自修这些业务语义。

### O. 最可能的架构失败是什么？

把诊断中心做成“又一套状态机＋每文件全量日志＋猜测式规则”：额外负载拖慢迁移，队列丢失又被当业务缺失，于是制造更确定的错误结论。防线是**观察者权威边界、每条事实可引用、缺证据可承认、资源/隐私预算前置、真实OFF对照、小步实施Gate**。

**建议审查顺序**：先批准§0/§5的边界与分层，再审§6–16的证据/损失契约，再决定§25预算及§32 D1授权；不要先画UI再补数据模型。当前文档完成不等于获得实施授权。
