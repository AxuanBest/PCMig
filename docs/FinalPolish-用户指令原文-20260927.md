PCMig v0.5.0 现在正式进入 Final Polish / 精修阶段。

这一阶段不是重新设计 UI，也不是再次大规模调整视觉方向。

Developer Visual Tuning 已经由我本人实际操作和验收，目前整体没有明显的大方向问题，Material / Desktop Acrylic / Layer 0–5 的基本方向已经合格。

从现在开始：

冻结大的视觉方向。
停止继续推翻式重构。
停止为了追求“另一种效果”而重新搭材质体系。

接下来的工作重点变为：

1. 恢复在 0.5.0 UI 重构过程中丢失的历史功能；
2. 建立真正可用的响应式窗口布局；
3. 修复我人工发现并标注出来的 UI 缺陷；
4. 建立统一、克制的 Motion / Transition 动画体系；
5. 对四个主页面、二级页面、浮层、状态栏等进行系统精修；
6. 建立不同窗口尺寸、比例、DPI 下的完整验收矩阵；
7. 把现在“已经像样”的 0.5.0 推进到真正完成度较高的 Windows 桌面应用。

3. 第二类严重问题：Responsive Layout / 自适应窗口布局缺失
==================================================

目前窗口缩小时会出现：

内容显示不全；
区域被裁切；
卡片无法完整显示；
控件仍保持大尺寸；
界面比例变得细长；
用户还能继续缩小窗口，即使 UI 已经不可用了。

这不合格。

PCMig 作为 Windows 桌面应用必须具有真正的窗口适配。

我要的总体原则是：

先响应式适配；
到合理极限以后；
再禁止继续缩小。

不是：

一直允许缩小，然后让内容消失。

Responsive 必须从真实 Layout 层做。

==================================================
5. 建立 Responsive Architecture
==================================================

建立窗口级响应式控制体系。

可以设计：

ResponsiveLayoutController

或者同等职责的实现。

至少跟踪：

WindowWidth；
WindowHeight；
EffectiveWidth；
EffectiveHeight；
AspectRatio；
DpiScale；
LayoutMode；

建议 LayoutMode 至少：

其中：

DensityScale 决定同一档位内部连续的视觉收紧。

不要让所有尺寸突然跳变。

==================================================
6. DensityScale 的作用
==================================================

可以把正常默认尺寸定义为：

1.00

窗口逐渐缩小时：

DensityScale 可以平滑下降。

例如最终实测可能是：

1.00 → 0.86

或者：

1.00 → 0.82

具体最低值不要拍脑袋。

通过真实 UI 验证以后决定。

重点：

DensityScale 不是把整个 UI 进行 RenderTransform 缩放。

它应该驱动 UI Token。

例如：

PageMargin；
WorkspacePadding；
CardPadding；
CardGap；
SectionGap；
SidebarWidth；
HeaderHeight；
BottomBarHeight；
IconSize；
ButtonHeight；
InputHeight；
BadgeSize；
部分 CornerRadius；
部分字号；
部分标题间距。

==================================================
7. Responsive 缩放优先级
==================================================

窗口变小时，优先：

第一：

缩小外围 Margin；

第二：

缩小区域之间 Gap；

第三：

缩小 Card Padding；

第四：

缩小装饰图标；

第五：

缩小部分按钮和 Input 高度；

第六：

必要时调整局部布局方向；

最后才是：

轻微缩小字体。

不要一开始就把文字缩小。

正文可读性要优先。

尤其不要把：

用户名；
密码；
路径；
共享名称；
状态；
日志；

缩得太小。

==================================================
8. 响应式必须适配不同屏幕比例
==================================================

不能只为目前这台屏幕调。

至少测试：

16:9；

16:10；

3:2；

接近普通办公窗口的较窄比例；

较宽比例。

如果用户把窗口缩成极端超窄、超扁：

不需要继续支持。

到了设计最低尺寸：

直接禁止继续缩小。

==================================================
9. Minimum Window Size 必须真正实现
==================================================

不要只在 XAML 上写：

MinWidth；
MinHeight；

然后实际 Win32 Window 仍然能继续缩。

必须验证 Windows 窗口层面的真实行为。

如果 WinUI 3 当前方案无法可靠限制：

使用 HWND + WM_GETMINMAXINFO。

设置：

MINMAXINFO.ptMinTrackSize

但不要直接随便写死一个尺寸。

正确流程：

先完成 Compact Layout；

找到：

四个主页面；
底栏；
侧栏；
关键按钮；
Developer Panel；

全部仍然能完整显示的最小 Effective DIP。

然后用这个尺寸作为窗口最小尺寸。

再根据 DPI 转换成真实 Win32 tracking size。

必须考虑：

100%；
125%；
150%；
175%；
200%。

不要混淆：

DIP；
Effective Pixel；
Physical Pixel。
