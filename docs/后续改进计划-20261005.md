# PCMig v0.5.0 · 后续改进计划（2026-10-05）

> 依据：本轮 UI Closure 返修（PHASE A–D）的实施与真机取证过程中暴露的问题、尚未闭环的验收项、
> 以及代码中已被证据定位的架构性隐患。
> 本文件是**计划**不是承诺：所有工作量估算以"熟练单人 + 本机环境"为基准，实际以证据为准。
> 纪律不变：无证据不写"已修"；不得降低断言、不得用 sleep 掩盖竞态、不得把请求成功当业务成功。

---

## 零、结论摘要

本轮修好了 4 个用户可见缺陷的**代码级根因**（提示卡堆叠、进度动效不可见、暂停回退、统计卡排版风险），
测试全绿（Core 493/493、Diagnostics 382/382、build 0 error），但**自动化终验证据只完成了一半**：
进度动效与 Resume 连续性有像素级/CSV 级证据；提示卡多通道与 DPI 多档仍缺；诊断中心展示面未接。

同时暴露 3 个**结构性隐患**（比单个 bug 更值得处理）：

1. **静默 `catch` 降级**：装饰物因负 DelayTime 抛异常后被 `catch` 吞掉并置 null，
   导致"扫描高光/粒子/柔光在屏幕上根本不存在"而无人知晓 —— 上一轮据此写了"已实现"，结论被证伪。
2. **一个字段承担两种语义**：`JobState.CompletedBytes` 同时是"完成回执字节"和"UI 曾显示的在途字节"，
   这正是 42.9%→24.8% 的根因土壤。
3. **UI 用魔法数补偿排版问题**：`LineHeight=32` 补裁切、`Width="68"` 覆盖 token 造成声明与渲染不一致。

这三点都值得单独立项，而不是等下一次缺陷暴露。

## 三、第 3 波：结构性改进（1–2 天量级，建议单独立项）

### 3.1 清理"静默 catch 降级"（P0，最高杠杆）
- **问题**：`ProgressMotionDriver.CreateDecorations` 的 `catch` 把 `_sweepVisual/_glowVisual/_particleHost` 置 null，
  既无日志也无 UI 提示 ⇒ 功能消失但无人知晓。同类写法很可能散布在别处。
- **行动**：
  1. 全仓审计 `catch {` / `catch (Exception) { }`（grep + 人工过一遍），逐条判定"必须记日志"还是"确实可忽略"；
  2. 强制规则：任何 UI/动效/装饰类对象创建失败，最少 `_log.Warning` + 诊断探针字段可见；
  3. 已在 `ProgressMotionDriver` 落地 `_decorationError` 探针字段与 `Decorations_MustBeReallyCreated` 契约测试，
     把该模式推广到其它装饰型组件（提示卡进动、页转场、Popup）。
- **验收**：审计清单（文件:行 + 判定 + 处置）归档；关键路径注入一次人为失败，探针/日志必须可见。

### 3.2 真值语义分层：Committed / Displayed / Diagnostic（P0）
- **问题**：`JobState.CompletedBytes` 一名两义，是 42.9→24.8 的根因土壤；
  `ProgressTruthSnapshot` 里 `CommittedBytes / InFlightConfirmedBytes / DisplayedTransferredBytes` 已是对的模型，
  但落到 job-state 与 VM 时又被压回一个字段。
- **行动**：
  1. 给 `JobState.CompletedBytes` 加语义锁注解（或重命名为 `CommittedBytes`，保留读兼容 shim，向后兼容读写）；
  2. 明确三层：**权威真值**（Completed Receipt，决定 skip/完成数/最终判定）→ **显示真值**（Presentation 合成，含 resume floor）
     → **诊断真值**（原始 raw 全量保留）；
  3. 所有 UI 只读"显示真值"，所有业务判定只读"权威真值"，诊断只读"诊断真值"——
     用契约测试锁死"业务判定不得引用显示真值"。
- **验收**：新增契约测试；`ResumeProgressReconstructionTests` / `P07` / `ResumeProgressContinuityTests` 全绿。

### 3.3 动画订阅语义事件，而非字符串差异（P1）
- **问题**：本轮已把提示卡通道路由动画降级为语义级（对象 ID 切换 / Collapsed→Visible / 空→有内容），
  但该策略散落在 `ShellHintCard.xaml.cs` 的 if 判断里，其它动效组件（页转场、卡片进动、Popup）无统一入口。
- **行动**：在 Presentation 层引入轻量"语义事件"约定（`ObjectSwitched` / `ChannelFirstShown` / `PhaseChanged`），
  动效组件只订阅语义事件；`StatusChannel` 已有类型基础，改造成本低。
- **验收**：新增契约测试"高频内容刷新不得触发位移动画"（提示卡已有先例，推广到其它通道）。

### 3.4 声明几何 vs 实际渲染的一致性检查（P1）
- **问题**：`FooterPercentWidth` 声明 48 / XAML 渲染 68（死代码不一致，本轮已对齐）；
  `LineHeight=32` 这类魔法数也是同一类病。
- **行动**：把本轮 `Batch5UiLayoutContractTests` 的"XAML 宽度 + 响应式 token 一致"检查
  扩展为**所有响应式 token × XAML 硬编码值**的自动比对；DPI 相关的排版数值全部改由引擎/容器决定。
- **验收**：新增契约测试覆盖全部 `ResponsiveLayoutController` 宽度/高度 token。

### 3.5 测试专用可控节流模式（P1，需在纪律下明确边界）
- **问题**：本机 C:→E: 顺序写 2.7–5 GB/s，42 GB 数据集整个运行只有 ~25 秒，
  且 UI 前 4.6 秒一直显示 0.0% ⇒ 中间态（低百分比 + 少量完成回执）极难命中，
  这正是 42.9→24.8 真机复现失败的**环境原因**，不是产品缺陷。
- **行动**：引入**仅测试构建可用**的 `PCMIG_TEST_THROTTLE=<MB/s>`（默认关闭，生产构建忽略），
  通过人为限速把 42 GB 拉长到数分钟，从而稳定复现中间态。
- **纪律边界（必须写进注释与文档）**：
  - 它不是"用 sleep 掩盖竞态"：它延长的是**真实 I/O 时长**，不改变任何状态机时序语义；
  - 不得在生产构建中生效；不得用它把失败测试"变绿"；只在取证与回归夹具里使用；
  - 使用它的每一份证据必须标注"throttled"。
- **验收**：throttled 下能稳定复现 42.9→24.8；未 throttle 的行为与现状一致（回归无差异）。

## 六、风险提示（按严重度）

1. **未提交风险（最高）**：当前工作树有 **90 项未提交改动**（57 改 + 33 新增），
   包含本轮全部修复与 2 份新文档。任何 `git reset --hard` / `checkout .` / `clean -fd` 都会导致本轮工作丢失。
   **建议尽快 commit**（需用户授权）。
2. **构建与运行互斥**：应用运行时 `dotnet build` 会因 `PCMig.WinUI.exe` 被占用而
   `MSB3021/MSB3027` 失败 ⇒ 所有脚本应固化"先 `Stop-Process -Name PCMig.WinUI` 再构建"。
3. **取证环境不稳定**：窗口位置每次启动不同（已观测 26,26 / 104,104 / 208,208 / 234,234），
   同一进程内 `TotalProgressHost` 的 y 随页面布局变化（345 / 430 / 472 / 518 / 570 / 592 / 644 均出现过）
   ⇒ 任何硬编码坐标必然失效，必须现取。
4. **安全软件拦截**：本机装有火绒（HipsDaemon）；大批量文件写入（本轮把数据集扩到 42 GB）前应先预警。
5. **测试并行抖动**：`PauseCoreSemanticsTests.P07` 在整套并行运行时曾偶发失败、单独运行通过
   ⇒ 涉及时间/暂停的测试建议标注为串行集合，避免把抖动误判为回归。
6. **调试旋钮泄漏生产**：`PCMIG_PROGRESS_DEBUG=1` 会启用高可见度装饰与屏幕浮层，
   若被误用到生产环境会直接改变 UI 外观 ⇒ 需要 4.5 的登记与默认关闭契约。
