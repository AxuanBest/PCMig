## 二、1｜Deep Trace E2E = FAIL（限定，含精确范围）

**做对的部分（有实测原文）**

* 真实开关：UIA TogglePattern 与**真实鼠标点击** (690,278) 都能开启；面板文本随之从「采集 Operational」变「采集 Deep」，环容量 4KiB/6 → 5KiB/8。
* 真实输入被观测到，且**显式 AutomationId 控件归属正确**：`Shell.Tool.MaterialTuning`、`Diagnostics.Refresh`、`Diagnostics.WarnOnly`、`Diagnostics.DeepTrace`。
* **按设计自动结束**：`21:09:10.817 → 21:10:10.857` = **60.04 s**，与 `src\PCMig.WinUI\Diagnostics\DeepTraceInputObserver.cs` 的 `DefaultMaxDuration = 60 s` 完全一致（另有 3 次窗口同构）。
* **去重与抑制计数可见**：真实双击只发布 2 条事件 + `suppressedDuplicates:6`（150 ms 窗口，`MaxDedupeEntries 256`），业务无副作用、无重复 Command。
* **不污染业务**：观测开启时输入照常生效（`Step1.Connect` 由 disabled → enabled），异常全程被吞掉。
* **隐私**：密码框来源整条丢弃，只有 `droppedSensitive` 计数（见 §三）。

**FAIL 的三条硬理由**

1. **端到端的"端"断了**：Deep Trace 窗口开了 8 次、ring 累计 68 条，但 `persistedWindows: 0`；本地 `flight\checkpoint-active.jsonl` 永远以 `active-segment-skipped` 被排除；**4 个导出包内 0 个 flight 文件**，而 manifest 一律声称 `includedFlightWindows: true` ⇒ Deep Trace 的产物**没有任何一条路径能进入交付证据**（12 个 Deep-only 事件同理）。
2. **`controlId="unknown"` 覆盖了大多数真实控件**：点 `HostInput`、点步骤卡都是 `unknown`；同一时刻点材质调节入口却能得到正确 ID ⇒ 解析器没问题，**根因是产品 XAML 未绑定 `ControlIds.cs` 注册的显式 AutomationId**（全仓 `SetAutomationId` 命中 0；`Views\Step1ConnectPage.xaml:22` 只有 `x:Name`）。这违反 `docs\方案-诊断中心与自诊断架构.md:199,207` 与 `docs\诊断系统实施-阶段证据.md:734` 的公开承诺，且 `unknown` **同时**表示"只有 x:Name"与"点到非控件表面/禁用控件"，诊断上不可区分。
3. **生命周期事件不对称**：自动到期**只发** `UI.InputObserved{deep-trace-stopped}`（4 次样本）、**不发** `DIA.ModeChanged`，且 UI 仍停在 Deep；手动关闭**只发** `DIA.ModeChanged{reasonCode:"user-disabled-deep-trace"}`（1 次样本）、**不发** `deep-trace-stopped` ⇒ 同一状态转换两侧各缺一半证据。

**附带限制（如实登记，非失败）**：UIA/自动化驱动的操作不产生输入事件 ⇒ "用户做了什么"对屏幕阅读器/自动化场景不可见（Not Instrumented）；禁用控件上的真实点击零业务事件 ⇒ 无法区分"没点到/打到表面/被 disabled 拒绝"。
