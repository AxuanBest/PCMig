**校准证据**（不是猜的）：

### 三条关键推断

1. **模块内偏移 6/6 完全相同（`0x7F9880`）**
   ⇒ 这是**同一处静态代码**的确定性故障，不是随机内存损坏、不是竞态、
   也不随线程 ID / 启动时刻变化（线程 ID 六个全不同）。

2. **ASLR 基址有 2 个不同值**（`0x7FFCCD480000` 与 `0x7FFCD3E10000`）
   ⇒ 归一化到模块内偏移是**必要且正确**的做法；
   若只看绝对地址会误判成两个不同的崩溃点。

3. **时间跨度 12:18 → 19:16（7 小时），跨两批启动**
   ⇒ 与本次修复工作**无因果关系**；该缺陷**先于本轮所有改动存在**。

### 故障写入地址（本轮新增，此前未知）

```
nParams = 2
ExceptionInformation[0] = 0  -> 读 (READ)
ExceptionInformation[1] = 0x58
```

**⇒ 在地址 `0x58` 处读取失败。**

`0x58` 是**很小的偏移**，且基址为 NULL ⇒ 这是典型的
**「已被销毁 / 未初始化对象的成员访问」**：
代码持有 `this`/对象指针为 `NULL`（或已被释放并置空），
然后读取该对象偏移 `0x58` 处的字段。
若为 C++ 虚调用，`0x58` 也可能是 vtable 槽位索引 ×8（= 第 11 个虚函数）。

**对比上一会话的另一崩溃族**（`Windows.ApplicationModel.LimitedAccessFeatures`，
退出码 `0xC000027B`）—— **本轮这个不是它**：异常码是 `0xC0000005`，
故障模块是 `Microsoft.UI.Xaml.dll`，两者是不同故障族。
**不要用「置灰按钮」那条已修结论来解释本崩溃。**

## 四、转储里拿不到的东西（如实说明）

| 想要 | 状态 | 原因 |
|---|---|---|
| 寄存器（RIP/RSP/RBP…） | **拿不到** | `ThreadContext` 描述符指向的段**前 256 字节全零**（已实测非零字节数 = 0） |
| 崩溃线程调用栈 | **拿不到** | 无寄存器 ⇒ 无 RSP ⇒ 无法回走栈；且 `ThreadList` 里的上下文同样为空 |
| 符号名/函数名 | **拿不到** | 需 `Microsoft.UI.Xaml.pdb`（微软符号服务器），本机无；本次未联网下载 |
| 出错源码行 | **拿不到** | 同上（`Microsoft.UI.Xaml.dll` 是闭源框架二进制） |

**转储配置**：`Flags = 0x200121`
= `MiniDumpWithDataSegs`(0x1) + `MiniDumpWithIndirectlyReferencedMemory`(0x20)
+ `MiniDumpWithProcessVmCounters`(0x200000)
**不含** `MiniDumpWithFullMemory`(0x2)、**不含** `MiniDumpWithThreadInfo`(0x1000)
⇒ 这正是上下文为空的直接原因。

**可选补救（需授权）**：
改 `HKLM\SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps`
的 `DumpType` 为 `2`（Full）后复现一次，即可拿到寄存器与完整栈 —— 属**系统级改动**，须当轮授权。

### 7.2 机制（issue 原文结论）
> The reason behind this crash is calling into **`threadpoolwinrt.dll` when it is already freed**.
> On process shutdown, dlls are unloaded in reverse load order...

即 `Microsoft.UI.Xaml.dll` 在 `DllMain(DLL_PROCESS_DETACH)` 里调
`ThreadPoolService::ReleaseFactories()` 释放缓存的线程池激活工厂，
但此时 `threadpoolwinrt.dll` **已被卸载**，工厂 vtable 指向已释放内存 ⇒ 解引用崩溃。

**框架方自述的修复方向**（issue 评论，Firecrawl 摘要节选）：
> The most obvious fix would be **not calling `ThreadPoolService::ReleaseFactories` if
> deinitialization happens due to process exiting.**

### 7.3 为什么"必然"是这条链（本项目侧独立佐证）
1. `0x7F9880` 经 PE 解析**落在 `Microsoft.UI.Xaml.dll` 的 `.text` 段内**
   （`.text` VA=`0x1000` VSize=`0xA075EF`）⇒ **确是 Xaml 自己的代码**。
2. 关闭期 `Microsoft.UI.Xaml.dll` **唯一会执行的自有代码就是它的 `DllMain`**
   —— 进程正在退出，无消息循环、无应用代码在跑。
   故"Xaml 模块内的读 NULL"只能是 `DllMain → DeinitializeDll → ReleaseFactories`。
3. 与"**零交互启动也崩**"完全相容：不需要任何应用行为，纯卸载顺序问题。
4. 与"**与页面内容无关**"（上一会话二分证明：内容全 Collapsed / Ctrl+4 不显示仍崩）相容。

## 八、结论（最终）

**这是 Windows App SDK 的框架级缺陷，不是 PCMig 的源码缺陷。**

`Microsoft.UI.Xaml.dll`（实测 `3.2.3.2609`，产品线 2.3）在
`DllMain(DLL_PROCESS_DETACH) → DeinitializeDll → ThreadPoolService::ReleaseFactories`
路径上释放已被卸载的 `threadpoolwinrt.dll` 中的线程池工厂；
在本项目转储中表现为**固定偏移 `+0x7F9880` 处读 NULL `+0x58`**，
**6/6 指纹一致、早于本轮全部改动、零交互启动亦复现、与页面内容无关**。

**可落地的规避方向（均需授权后实测，本轮均未做）**：

| # | 方向 | 依据 | 风险 |
|---|---|---|---|
| 1 | 关闭时先显式清理 thread-pool 支持的 WinRT 对象（`MotionState` 的定时器字典），再让进程退出 | §7.4 | 低（纯清理，不动冻结逻辑） |
| 2 | 关闭路径改为显式结束进程（如 `Environment.Exit(0)`），绕开 `LdrShutdownProcess` 的 Xaml 卸载 | §7.2 框架方修复方向 | 中（可能只把崩溃点后移，**必须实测 WER 增量**） |
| 3 | 接受为已知平台缺陷：关闭无用户可见失败，仅 WER 留痕；在交付说明中如实披露 | —— | 无（但 WER 清洁闭环**不达标**） |
| 4 | 装完整转储（WER `LocalDumps\DumpType=2`）复现一次，以**确证**谓词 | §四 | 需系统级改动授权 |
